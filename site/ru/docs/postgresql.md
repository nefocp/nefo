# PostgreSQL

Nefo запускает PostgreSQL рядом с MariaDB или MySQL: версию вашего дистрибутива или основную версию с 15 по 19 из собственного репозитория проекта PostgreSQL (apt.postgresql.org). Вкладка **Базы данных** → **PostgreSQL** создаёт базы данных с их владельцами, импортирует и экспортирует их, открывает отдельную базу данных для выбранных адресов через TLS и обновляет сервер до новой основной версии, предварительно сделав дамп.

PostgreSQL — сервер баз данных, который предпочитают многие приложения на Laravel, Django, Node.js и Odoo. MariaDB (или MySQL) и PostgreSQL могут работать рядом. О MariaDB и MySQL см. [Базы данных](./databases).

## Установка PostgreSQL {#install-postgresql}

1. Откройте **Программы** → **PostgreSQL** и нажмите **Установить**.
2. В поле **Версия** выберите, какой PostgreSQL установить:
   - версию вашего дистрибутива, например «PostgreSQL 16, версия дистрибутива», с отметкой **Рекомендуется**. Она обновляется вместе с системой;
   - версию из apt.postgresql.org, например «PostgreSQL 18 из apt.postgresql.org», и другие основные версии, которые предлагает репозиторий проекта PostgreSQL. Выбирайте её, когда приложению нужна более новая (или более старая) версия, чем в вашей системе.
3. Нажмите **Установить** и подождите минуту-другую. Журнал выполнения показывает каждый шаг.

| Система | Версия дистрибутива | Из apt.postgresql.org |
|---|---|---|
| Ubuntu 22.04 | 14 | 15, 16, 17, 18, 19 |
| Ubuntu 24.04 | 16 | 15, 17, 18, 19 |
| Ubuntu 26.04 | 18 | 15, 16, 17, 19 |
| Debian 12 | 15 | 16, 17, 18, 19 |
| Debian 13 | 17 | 15, 16, 18, 19 |

Панель предлагает основные версии, которые проект PostgreSQL ещё поддерживает. В другой системе или на процессоре, для которого в репозитории нет пакетов, предлагается только версия дистрибутива, и диалог объясняет почему.

Если вы выбрали версию из apt.postgresql.org, панель:

- скачивает ключ подписи репозитория с `https://www.postgresql.org/media/keys/ACCC4CF8.asc` и отклоняет его, если его отпечаток не `B97B 0AFC AA1A 47F0 44F2 44A0 7FCC 7D46 ACCC 4CF8` (ключ «PostgreSQL Debian Repository»);
- записывает его в `/etc/apt/keyrings/panel-pgdg.gpg` и добавляет `/etc/apt/sources.list.d/panel-pgdg.list`, который доверяет этому ключу только для этого репозитория;
- устанавливает пакет сервера по его имени, например `postgresql-18`. Пакет `postgresql` из этого репозитория она никогда не устанавливает, потому что он всегда тянет за собой новейшую основную версию, и тогда обновление системы добавило бы второй сервер.

Обновления безопасности для обеих версий приходят с обновлениями системы (страница **Система** или `apt upgrade`).

Затем карточка на странице **Программы** показывает **Из дистрибутива** или **Из apt.postgresql.org**, и то же самое видно вверху вкладки **Базы данных** → **PostgreSQL**.

Одновременно работает только одна версия PostgreSQL. Панель не позволяет установить:

- другую версию, пока одна уже установлена. Вместо этого [обновите](#upgrade-postgresql) её или сначала удалите;
- версию, отличную от той, чьи данные остались на сервере от прежней установки (в `/var/lib/postgresql/<version>`). Чтобы использовать эти данные, снова установите ту же версию, а затем при желании обновите её, или сначала удалите данные.

apt работает с локалью C, поэтому кластер, который создаёт пакет, хранит текст как `SQL_ASCII`. Затем Nefo создаёт этот новый, ещё пустой кластер заново с UTF-8 (`C.UTF-8`). Кластер, который существовал до установки, никогда не пересоздаётся.

## Как настраивается PostgreSQL {#how-postgresql-is-tuned}

Nefo записывает свои настройки в `/etc/postgresql/<version>/main/conf.d/90-nefo.conf`. Настройки памяти зависят от объёма оперативной памяти сервера:

| Память сервера | `shared_buffers` | `effective_cache_size` | `work_mem` | `maintenance_work_mem` | `max_connections` |
|---|---|---|---|---|---|
| Меньше 768 MB | 64MB | 256MB | 2MB | 16MB | 30 |
| 768 MB и больше | 128MB | 512MB | 4MB | 32MB | 40 |
| 1,5 GB и больше | 256MB | 1024MB | 4MB | 64MB | 50 |
| 3 GB и больше | 512MB | 2048MB | 8MB | 128MB | 75 |
| 7 GB и больше | 1024MB | 4096MB | 16MB | 256MB | 100 |

`effective_cache_size` — примерно половина оперативной памяти, потому что на том же сервере работают также веб-сервер, PHP и, возможно, MariaDB. На всех серверах Nefo также задаёт `listen_addresses = 'localhost'`, `password_encryption = 'scram-sha-256'`, `random_page_cost = 1.1` (для SSD) и `jit = off`. На VPS-контейнере (LXC) объём оперативной памяти — это лимит памяти контейнера (см. [VPS в контейнере](./first-steps#a-vps-that-is-a-container)).

В простое и без данных PostgreSQL нужно примерно 30–40 MB на несколько фоновых процессов. По мере заполнения кэша он растёт до `shared_buffers` плюс около 40 MB, а каждое открытое подключение добавляет несколько MB. Страница **Программы** показывает `shared_buffers` плюс 40 MB.

::: warning
Не редактируйте `90-nefo.conf` и `pg_hba.conf`. Повторная установка PostgreSQL перезаписывает их. Ваши собственные строки в `pg_hba.conf` сохраняются, когда вы меняете удалённый доступ: панель трогает только свои строки (см. [Удалённый доступ](#postgresql-remote-access)).
:::

## Кто может подключаться {#who-can-connect}

Nefo записывает `/etc/postgresql/<version>/main/pg_hba.conf`:

```
local   all  postgres                peer
local   all  all                     scram-sha-256
host    all  all       127.0.0.1/32  scram-sha-256
host    all  all       ::1/128       scram-sha-256
```

- Без пароля через локальный сокет входит только системный пользователь `postgres`. Так панель управляет сервером.
- Всем остальным нужен пароль, через сокет или по TCP с этого сервера. В отличие от настроек дистрибутива по умолчанию, другие пользователи Linux не получают входа без пароля («peer»), поэтому пользователь Linux сайта не может открыть роль базы данных с тем же именем без её пароля.
- Другие машины подключаться не могут, если вы не разрешите их адрес для одной базы данных (см. [Удалённый доступ](#postgresql-remote-access)). Пока ни одна база данных не разрешает удалённый доступ, PostgreSQL слушает только localhost.

## Создание базы данных PostgreSQL {#create-a-postgresql-database}

1. Откройте **Базы данных** → **PostgreSQL** и нажмите **Добавить базу данных**.
2. Введите имя в поле **База данных**. Владельцем базы данных становится роль с тем же именем.
3. Оставьте поле **Пароль** пустым, чтобы получить надёжный случайный пароль, или введите свой.
4. Необязательно: выберите сайт в поле **Сайт**. Тогда резервная копия этого сайта будет включать эту базу данных, а при удалении сайта вместе с его базами данных удалится и она.
5. Нажмите **Создать базу данных**.

Карточка с данными для подключения показывает **База данных**, **Пользователь**, **Пароль**, **Хост** (`localhost`) и **Порт** (`5432`). Например, для приложения Laravel задайте `DB_CONNECTION=pgsql`, `DB_HOST=127.0.0.1`, `DB_PORT=5432`, а также базу данных, пользователя и пароль с карточки.

Правила:

- Имена и пароли подчиняются [правилам MariaDB](./databases#create-a-database). Собственные имена PostgreSQL тоже не принимаются: `postgres`, `template0`, `template1`, `public`, `all` и всё, что начинается с `pg_`.
- Одно имя нельзя использовать на обоих серверах: если база данных или пользователь MariaDB называется `shop`, базу данных PostgreSQL так назвать нельзя, и наоборот. Панель также не принимает имя, которое PostgreSQL уже использует для базы данных или роли.
- Роль может входить, не является суперпользователем и не может создавать базы данных и роли. Никакая другая роль не может подключаться к базе данных, потому что панель отзывает `CONNECT` у всех остальных.
- Новые базы данных используют UTF-8 с локалью `C.UTF-8`.

Пароль никогда не попадает в PostgreSQL открытым текстом: панель отправляет только его проверочное значение SCRAM-SHA-256, поэтому он не может оказаться и в журнале PostgreSQL.

**Показать данные для входа**, **Новый пароль** и **Удалить** работают так же, как для MariaDB. Удаление также закрывает открытые подключения к базе данных и удаляет её строки удалённого доступа и правила брандмауэра. База данных, удалённая не через панель, помечается **Не найдена в PostgreSQL**.

## Могут ли другие серверы подключаться к базе данных PostgreSQL? {#postgresql-remote-access}

Да, начиная с v0.24.0, для каждой базы данных отдельно. По умолчанию PostgreSQL принимает подключения только с самого сервера. Можно разрешить выбранным адресам подключаться к одной базе данных с собственным пользователем (ролью) и паролем этой базы данных, через TLS.

Прежде чем начать, установите брандмауэр ufw на странице **Брандмауэр и SSH** и включите его. Пока ufw не установлен, панель не позволяет включить удалённый доступ.

1. Откройте **Базы данных** → **PostgreSQL**, откройте меню базы данных и выберите **Удалённый доступ**.
2. В разделе **Разрешённые адреса** введите адрес. Чтобы добавить ещё, нажмите **Добавить адрес**.
3. Нажмите **Сохранить**.

После этого в строке появляется «Удалённо: 1» (число адресов), а вверху вкладки — «1 открыта для других серверов».

Подключайтесь к публичному IP-адресу сервера с пользователем и паролем из **Показать данные для входа** и с TLS, например:

```sh
psql "host=203.0.113.10 port=5432 dbname=shop user=shop sslmode=require"
```

### Разрешённые адреса {#allowed-addresses}

- Отдельные адреса IPv4 или IPv6, например `198.51.100.7` или `2001:db8::1`.
- Диапазоны в форме CIDR: IPv4 не шире `/16` (например, `198.51.100.0/24`), IPv6 не шире `/48` (например, `2001:db8:5::/48`).
- Не больше 10 адресов на базу данных.
- Адреса loopback, link-local (`fe80::`), `0.0.0.0`, `::` и адреса multicast не принимаются.

### Что меняет панель {#what-the-panel-changes}

| Где | Изменение |
|---|---|
| `pg_hba.conf` (PostgreSQL 16 и новее) | Одна строка в конце, `include_if_exists nefo-remote.conf`, с комментарием. Разрешённые адреса находятся в `/etc/postgresql/<version>/main/nefo-remote.conf` |
| `pg_hba.conf` (PostgreSQL 14 и 15) | Блок в конце между `# BEGIN Nefo remote access` и `# END Nefo remote access` |
| Эти строки | По одной на адрес, только для этой базы данных и её собственной роли, со входом по паролю: `hostssl "shop" "shop" 198.51.100.7/32 scram-sha-256` |
| Настройки PostgreSQL | `/etc/postgresql/<version>/main/conf.d/95-nefo-remote.conf` задаёт `listen_addresses = '*'`. Файл существует, только пока хотя бы одна база данных разрешает удалённый доступ |
| Брандмауэр (ufw) | Для каждого адреса — правило, которое разрешает порт кластера (по умолчанию 5432) по TCP только с этого адреса, с комментарием `PostgreSQL name` |

Остальные строки `pg_hba.conf` панель никогда не меняет. Если ваши собственные строки стоят раньше строк панели, они читаются первыми: ваша строка `reject` для того же адреса имеет приоритет. Прежде чем PostgreSQL перечитает изменённый `pg_hba.conf`, панель просит PostgreSQL проверить его (`pg_hba_file_rules`). Если PostgreSQL находит ошибку, старые файлы возвращаются на место и ничего не меняется.

Если кластер использует не порт 5432, а другой, правила брандмауэра используют этот порт, и он же указан в данных для подключения.

### Шифрование {#encryption}

Диалог сообщает, шифруются ли подключения с других машин:

- **Подключения с других машин шифруются**: строки имеют тип `hostssl`, поэтому PostgreSQL отклоняет подключения с этих адресов без TLS. Клиентам нужен `sslmode=require` (или строже). Debian и Ubuntu создают кластеры с самоподписанным сертификатом системы (`/etc/ssl/certs/ssl-cert-snakeoil.pem`). Если в кластере TLS выключен, панель создаёт собственный самоподписанный сертификат (`nefo-ssl.crt` и `nefo-ssl.key` рядом с `pg_hba.conf`) и включает TLS в `95-nefo-remote.conf`; с выключением последнего удалённого доступа TLS снова выключается. Оба сертификата самоподписанные, поэтому клиент не может проверить по ним сервер: `sslmode=require` шифрует, но `verify-ca` и `verify-full` не пройдут, если вы не установите собственный сертификат.
- **Подключения с других машин не шифруются**: у PostgreSQL нет TLS, поэтому строки имеют тип `host`. Для всего конфиденциального используйте SSH-туннель или VPN.

### Перезапуски {#restarts}

Новое значение `listen_addresses` требует перезапуска; для разрешённых адресов и TLS достаточно перечитать конфигурацию. Поэтому PostgreSQL перезапускается при первом включении удалённого доступа и ещё раз, когда он выключается для последней базы данных. Сайты теряют подключение к базе данных на несколько секунд, а открытые транзакции отменяются. Последующее добавление или удаление адресов перезапуска не вызывает.

Если в этот момент выполняется другая задача, диалог сообщает: **Чтобы принимать подключения с других машин, PostgreSQL нужно перезапустить.** Когда задача закончится, нажмите в диалоге **Перезапустить**.

Если PostgreSQL не запускается с `95-nefo-remote.conf`, панель удаляет этот файл и запускает PostgreSQL без него, чтобы ваши сайты продолжали работать.

::: warning
- Если брандмауэр выключен, порт открыт для всех. PostgreSQL всё равно впускает только указанные адреса и только с паролем.
- Указывайте только адреса, которые вы контролируете и которые не меняются.
:::

Чтобы выключить удалённый доступ, снова откройте **Удалённый доступ** и нажмите **Выключить**. При удалении базы данных удаляются также её строки и правила брандмауэра; если это была последняя база данных с удалённым доступом, PostgreSQL перезапускается, чтобы снова слушать только localhost.

## Экспорт и импорт базы данных PostgreSQL {#export-and-import-a-postgresql-database}

**Экспорт в .sql.gz** скачивает обычный SQL-дамп, сжатый gzip, который создаётся командой `pg_dump` от имени собственной роли базы данных с `--no-owner --no-privileges`, поэтому он импортируется в любую базу данных.

**Импорт** принимает файл `.sql` или `.sql.gz` размером до 4 GB:

- `psql` выполняется от имени собственной роли базы данных, никогда не от имени `postgres`, а её пароль хранится во временном файле, который может читать только root.
- Файл выполняется в одной транзакции с `ON_ERROR_STOP`: если инструкция завершается ошибкой, ничего не импортируется, а в ошибке указана строка.
- Собственные команды psql, строки, которые начинаются с обратной косой черты (например, `\connect`, `\!` или `\copy`), не принимаются: psql работает от имени root, и эти команды могли бы запускать программы или записывать файлы на сервере. Панель запускает psql в ограниченном режиме (`\restrict` со случайным ключом) и убирает строки `\restrict` и `\unrestrict`, которые пишут новые версии `pg_dump`. psql без ограниченного режима (старше 17.6, 16.10, 15.14 или 14.19) отклоняет любой импорт: сначала установите обновления системы.
- Инструкции, которые создают или меняют роли, передают объекты другим ролям или требуют суперпользователя, завершаются ошибкой. Экспортируйте такой дамп заново с `pg_dump --no-owner --no-privileges`.
- `SET transaction_timeout`, который пишет `pg_dump` 17 и новее, на более старых серверах пропускается.
- После импорта панель снова задаёт пароль роли на случай, если файл его изменил.

Если отмечено **Сначала очистить базу данных (удалить всё её содержимое)**, перед импортом база данных удаляется и создаётся заново с той же ролью-владельцем.

## Обновление PostgreSQL до новой версии {#upgrade-postgresql}

Сервер можно перевести на более новую основную версию из apt.postgresql.org, например с версии 15 из дистрибутива на 17, с сохранением всех баз данных, пользователей, паролей и настроек удалённого доступа.

1. Откройте **Базы данных** → **PostgreSQL** и нажмите **Обновить версию**. Кнопка появляется, когда предлагается более новая версия и PostgreSQL работает.
2. Выберите **Новая версия**.
3. Прочитайте **Что произойдёт** и отметьте **Я понимаю, что во время обновления сайты и приложения теряют доступ к базе данных.**
4. Нажмите **Обновить до 17** (выбранная вами версия) и следите за журналом.

Что делает панель, по порядку:

1. Проверяет, что новая версия новее, что кластер один (`main`), что для старой версии не установлены пакеты расширений (например, `postgresql-15-postgis-3`) и что на диске хватает места для удвоенного объёма данных плюс 256 MB.
2. Сохраняет все базы данных с помощью `pg_dumpall` в один сжатый файл, `/var/backups/nefo-postgresql/postgresql-<old>-before-<new>-<date>.sql.gz`, доступный для чтения только root. Пока ничего не изменилось: если дамп не удался, обновление на этом останавливается.
3. Удаляет пакет `postgresql` из дистрибутива, который только указывает на версию (из apt.postgresql.org он указывал бы на новейшую и установил бы второй сервер), предварительно пометив `postgresql-<old>` как установленный вручную. Затем добавляет репозиторий apt.postgresql.org, если его ещё нет, и устанавливает `postgresql-<new>`. Пустой кластер, который создаёт этот пакет, удаляется. Если apt тянет за собой какой-либо другой сервер PostgreSQL, обновление останавливается и откатывается.
4. Запускает `pg_upgradecluster -v <new> -m upgrade <old> main`. На это время PostgreSQL остановлен: около минуты для небольшого сервера, дольше для больших баз данных. `pg_upgrade` копирует файлы данных, поэтому старый кластер остаётся как был.
5. Передаёт новому кластеру старый `pg_hba.conf`, настройки панели (`conf.d/90-nefo.conf`) и настройки удалённого доступа (начиная с версии 16 разрешённые адреса переезжают в `nefo-remote.conf`), перезапускает его и проверяет, что он работает на том же порту с теми же базами данных и что каждая из них отвечает.
6. Только после этого удаляет старый кластер и его пакеты (`postgresql-<old>` и `postgresql-client-<old>`).

Если сбой происходит на шагах с 3 по 5, панель выполняет откат: удаляет новый кластер и пакеты новой версии, возвращает настройки старого кластера и снова запускает его. В конце журнала будет «PostgreSQL 15 runs again with its data as before» (PostgreSQL 15 снова работает с прежними данными). Ваши базы данных остаются такими, как были. Репозиторий apt.postgresql.org остаётся, если из него уже устанавливались пакеты, потому что `postgresql-common` и `libpq5` были обновлены из него и иначе перестали бы получать обновления; пакет `postgresql` из дистрибутива обратно не устанавливается.

Панель не позволяет обновить версию и указывает причину в диалоге, если:

| Причина | Что делать |
|---|---|
| Для старой версии установлены пакеты расширений | pg_upgrade нужны те же расширения, собранные для новой версии, а панель их не устанавливает. Обновите вручную через `pg_upgradecluster`, предварительно установив их для новой версии, или сначала удалите расширения |
| Существует больше одного кластера | Панель управляет только `main`. Обновите вручную |
| Не хватает места на диске | Освободите столько, сколько указано в сообщении |

База данных, которую `pg_upgrade` не может перенести, например таблица со столбцом `regproc`, приводит к сбою на шаге 4; тогда панель выполняет откат, как описано выше.

### Сохранённые дампы {#the-dumps-kept}

Сохранённый файл в любом случае остаётся в `/var/backups/nefo-postgresql`, а вкладка **PostgreSQL** показывает его в разделе **Сохранённые дампы**: для какого обновления он сделан (например, «PostgreSQL 15 → 17»), когда, его размер и путь. Когда убедитесь, что всё работает, удалите его кнопкой **Удалить этот дамп**.

Чтобы вручную восстановить из него всё на чистом сервере:

```sh
zcat postgresql-15-before-17-20261127-101500.sql.gz | runuser -u postgres -- psql -X -d postgres
```

## PostgreSQL в Adminer {#postgresql-in-adminer}

Для работы с PostgreSQL Adminer нужно расширение PHP `pgsql`. Панель устанавливает его для версии PHP, на которой работает Adminer, и только вместе с PostgreSQL: когда вы устанавливаете PostgreSQL при уже установленном Adminer или Adminer при уже установленном PostgreSQL. Adminer, установленный более ранней версией панели (сборка только для MySQL), при этом заменяется.

**Открыть в Adminer** в строке базы данных открывает вход PostgreSQL в Adminer, где уже заполнены сервер `localhost`, пользователь и база данных. Введите пароль из **Показать данные для входа**.

## PostgreSQL в резервных копиях {#postgresql-in-backups}

Резервные копии сайтов включают базы данных PostgreSQL сайта, а резервная копия базы данных может содержать одну базу данных PostgreSQL, вручную или по расписанию. Дамп — обычный вывод `pg_dump`, созданный от имени роли базы данных и сохранённый в архиве как `postgres/<name>.sql` рядом с дампами MariaDB.

Резервное копирование, экспорт и импорт используют `pg_dump` и `psql` установленной версии, из дистрибутива или из apt.postgresql.org, и порт кластера, даже если это не 5432.

При восстановлении каждая база данных очищается (удаляется и создаётся заново с той же ролью-владельцем), а дамп импортируется от имени этой роли. База данных, удалённая после создания резервной копии, создаётся заново — с паролем роли из резервной копии, если он там есть (начиная с v0.24.0), иначе с новым паролем.

## Удаление PostgreSQL {#uninstall-postgresql}

PostgreSQL удаляется на странице **Программы**. Панель не позволяет это сделать, пока в PostgreSQL есть хоть одна база данных, кроме `postgres`, `template0` и `template1`, включая базы данных, созданные не через панель. Также панель не позволяет удалить PostgreSQL, пока он остановлен, потому что тогда она не может это проверить. Данные в `/var/lib/postgresql` и настройки в `/etc/postgresql` сохраняются, если вы не отметите флажок и не введёте `postgresql`. См. [Программное обеспечение](./software#postgresql).

При удалении также удаляются репозиторий apt.postgresql.org и его ключ, если их добавила панель, и все оставшиеся правила брандмауэра для баз данных PostgreSQL. Если расширению PHP `pgsql` (добавленному для Adminer) всё ещё нужен `libpq5`, панель возвращает `libpq5` к версии дистрибутива, чтобы он снова получал обновления безопасности вашей системы.

В магазине приложений также есть PostgreSQL в виде Docker-сервиса на 127.0.0.1 для приложений, которым нужен собственный сервер. Он не отображается на странице **Базы данных**: см. [Магазин приложений](./apps#install-a-service).
