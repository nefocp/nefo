# API-ключи

API-ключ позволяет скрипту пользоваться панелью Nefo без браузера: например, развернуть сайт из CI, запустить резервное копирование из задания cron на другом сервере или читать состояние сайтов из системы мониторинга. Ключ даёт доступ только для чтения или полный доступ, его можно ограничить перечисленными вами адресами, и у него может быть срок действия.

Скрипт отправляет ключ с каждым запросом как Bearer-токен — на тот же адрес и секретный путь, что и у панели.

Ключи находятся в разделе **Настройки** → **API-ключи**.

## Что может ключ {#what-a-key-can-do}

У каждого ключа один из двух видов доступа:

- **Только чтение**: только запросы `GET` и `HEAD`. Такой ключ может получать списки сайтов, баз данных и резервных копий, читать журналы задач, статистику и состояние сервера, но ничего не может изменить. Кроме того, он не может читать то, что дало бы ему больше возможностей: пароли баз данных и приложений, экспорт баз данных, файлы (файловый менеджер), скачивание резервных копий, значения Redis и секреты Git-вебхуков. На такие запросы, как и на любой запрос, кроме `GET` и `HEAD`, приходит `403` с `api_key_read_only`.
- **Полный доступ**: любые запросы, которые делают страницы самой панели, от вашего имени.

Даже ключ с полным доступом не может:

- создавать, просматривать или отзывать API-ключи;
- менять пароль или двухфакторный вход либо выходить из системы (всё, что под `/api/auth/`);
- открывать веб-терминал или терминал контейнера;
- пользоваться инструментами баз данных, закрытыми входом в панель, — Adminer и phpMyAdmin.

На такие запросы приходит `403` с `api_key_forbidden`: для них войдите в панель. Кроме того, ключом нельзя войти, чтобы получить сеанс.

::: warning
Ключ с полным доступом обладает теми же возможностями, что и вы: он может записывать файлы, добавлять задания cron, которые выполняются от имени root, и устанавливать программы. Храните его в таком же секрете, как пароль root. Ключ только для чтения — тоже секрет: с ним можно прочитать настройки, журналы и списки ваших сайтов и сервера.
:::

## Создание ключа {#create-a-key}

1. Перейдите в **Настройки** → **API-ключи** и нажмите **Новый ключ**.
2. Введите **Имя**, например `deploy-bot`: до 32 букв, цифр, пробелов, точек, дефисов и подчёркиваний. Имя показывается в журнале действий.
3. Выберите **Только чтение** или **Полный доступ**.
4. Необязательно: в поле **Разрешённые адреса (необязательно)** введите IP-адреса или сети, с которых можно использовать ключ, например `203.0.113.7` или `198.51.100.0/24`, IPv4 или IPv6, через пробел или с новой строки. Оставьте поле пустым, чтобы разрешить любой адрес.
5. Выберите, когда ключ **Истекает**: через 30, 90 или 365 дней либо **Никогда**.
6. Нажмите **Новый ключ**.

Панель показывает ключ один раз, с кнопкой **Копировать**: скопируйте его сейчас, больше вы его не увидите. Ключ выглядит как `nefo_` и 43 случайных символа. Панель хранит только его хеш SHA-256.

В списке для каждого ключа показаны имя и первые символы (например, `nefo_Ab12cd…`), вид доступа, разрешённые адреса, когда и откуда он использовался в последний раз (обновляется не чаще раза в минуту) и когда он истекает. Можно создать до 20 ключей. Чтобы отозвать ключ, нажмите его значок корзины и подтвердите: следующий запрос с ним не пройдёт.

## Вызов API {#call-the-api}

Передавайте ключ в заголовке `Authorization` как Bearer-токен. Адрес — это адрес панели с секретным путём, затем `api/` и маршрут:

```sh
export NEFO_KEY='nefo_…'
export NEFO='https://panel.example.com:PORT/<entrance>'

curl -H "Authorization: Bearer $NEFO_KEY" "$NEFO/api/sites"
```

- Ключ читается только из заголовка `Authorization`: никогда из адреса (`?key=`) или cookie.
- Запросу с телом JSON нужен `Content-Type: application/json`. Неизвестные поля отклоняются.
- Запросам с ключом не нужен заголовок `X-Requested-With`, который отправляют страницы самой панели.
- Обращайтесь к панели по HTTPS с настоящим сертификатом (**Настройки** → **Сертификат**, см. [Безопасность](./security#https-from-the-first-start)). Не используйте `curl -k`: так ключ попадёт к любому, кто окажется посередине.

Долгие задачи, такие как резервное копирование, развёртывание и сертификаты, выполняются в фоне. На их запрос приходит ответ `202` с задачей:

```json
{ "id": "a1b2c3", "kind": "backup", "target": "example.com", "status": "running", "log": [], "started": "…" }
```

Запрашивайте `GET /api/jobs/{id}`, пока её `status` не станет `succeeded` или `failed`; в `log` находятся её строки, а в `error` — причина ошибки. Панель выполняет одну задачу за раз: пока выполняется другая, новая получает ответ `409` с `busy`.

## Примеры {#examples}

Маршруты — те же, что используют страницы панели. Замените `3` на `id` вашего сайта.

### Список сайтов {#list-the-websites}

```sh
curl -s -H "Authorization: Bearer $NEFO_KEY" "$NEFO/api/sites"
```

Ответ: `{"sites": [{"id": 3, "domain": "example.com", "ssl": true, …}]}`. Достаточно ключа только для чтения.

### Резервное копирование сайта {#back-up-a-website}

```sh
curl -s -X POST -H "Authorization: Bearer $NEFO_KEY" -H "Content-Type: application/json" \
  -d '{"kind": "site", "target": "example.com", "remote": true}' \
  "$NEFO/api/backups"
```

- `kind` — это `site` (`target` — домен), `database` (имя базы данных), `folder` (абсолютный путь) или `app` (имя приложения из магазина приложений).
- `remote: true` дополнительно загружает резервную копию в удалённое хранилище, если оно настроено (см. [Резервные копии](./backups#remote-storage)).

Ответ — `202` с задачей. Чтобы дождаться её завершения:

```sh
JOB=$(curl -s -X POST -H "Authorization: Bearer $NEFO_KEY" -H "Content-Type: application/json" \
  -d '{"kind": "database", "target": "shop", "remote": false}' "$NEFO/api/backups" | jq -r .id)
while [ "$(curl -s -H "Authorization: Bearer $NEFO_KEY" "$NEFO/api/jobs/$JOB" | jq -r .status)" = running ]; do
  sleep 5
done
```

### Развёртывание из Git {#deploy-from-git}

Сначала настройте репозиторий на вкладке сайта **Развёртывание из Git** (см. [Развёртывание из Git](./git-deploy)). Затем вызывайте из CI после прохождения тестов:

```sh
curl -fsS -X POST -H "Authorization: Bearer $NEFO_KEY" "$NEFO/api/sites/3/git/deploy"
```

Тело запроса не нужно, ответ — `202` с задачей. В workflow GitHub Actions храните ключ и адрес в секретах репозитория:

```yaml
- name: Deploy
  run: curl -fsS -X POST -H "Authorization: Bearer ${{ secrets.NEFO_KEY }}" "${{ secrets.NEFO_URL }}/api/sites/3/git/deploy"
```

### Установка сертификата {#install-a-certificate}

Чтобы получить бесплатный сертификат Let's Encrypt (см. [SSL-сертификаты](./ssl)):

```sh
curl -s -X POST -H "Authorization: Bearer $NEFO_KEY" "$NEFO/api/sites/3/ssl"
```

Ответ — `202` с задачей. Чтобы вместо этого пройти проверку через Cloudflare DNS, которая нужна для wildcard-имён, отправьте `-H "Content-Type: application/json" -d '{"dns": true}'`.

Чтобы установить собственный сертификат, например продлённый на другом сервере, отправьте сертификат с цепочкой и закрытый ключ в формате PEM, всего до 256 KB. JSON из файлов собирает `jq`:

```sh
jq -n --rawfile cert fullchain.pem --rawfile key privkey.pem '{cert: $cert, key: $key}' |
  curl -s -X POST -H "Authorization: Bearer $NEFO_KEY" -H "Content-Type: application/json" \
    --data-binary @- "$NEFO/api/sites/3/certificate"
```

Ответ — `200` с сайтом и списком `warnings` или `400` с причиной, например если ключ не подходит к сертификату (см. [Собственный сертификат](./ssl#use-your-own-certificate)).

## Ошибки {#errors}

Ошибки возвращаются в JSON, например `{"error": "invalid_api_key"}`, иногда с полем `detail`.

| Статус | `error` | Значение |
|---|---|---|
| 401 | `invalid_api_key` | Ключ неизвестен, отозван или истёк либо используется с адреса, который он не разрешает. Ответ не говорит, что именно; это видно в журнале действий. |
| 403 | `api_key_read_only` | Ключ только для чтения отправил запрос, отличный от `GET` или `HEAD`, либо запросил пароль, файл, экспорт или скачивание резервной копии. |
| 403 | `api_key_forbidden` | Это может сделать только сеанс после входа (см. [Что может ключ](#what-a-key-can-do)). |
| 429 | `too_many_attempts` | Слишком много неудачных попыток с этого адреса. Подождите `retry_after` секунд; это значение есть и в заголовке `Retry-After`. |
| 400 | например, `bad_request` | Запрос неверен; `detail` может пояснить, что не так. |
| 404 | `not_found` | Объект не существует. Путь вне секретного пути получает простой ответ 404. |
| 409 | `busy` | Выполняется другая задача. Повторите попытку, когда она завершится. |

## Неудачные попытки и fail2ban {#failed-attempts-and-fail2ban}

Неудачная попытка с ключом учитывается как неудачный вход, в том же счётчике (см. [Ограничения входа](./security#sign-in-limits)): 5 неудач за 15 минут блокируют адрес на 15 минут — и для ключей, и для страницы входа. Действительный ключ счётчик не обнуляет.

Каждая неудача записывается в **Учётная запись** → **Последние действия** как «Неудачный вход» с причиной: `unknown API key`, `API key expired` или `API key not allowed from this address`. Jail панели в fail2ban читает эти записи и блокирует адрес, который продолжает подбирать ключ (см. [Защита от подбора паролей](./security#brute-force-protection-fail2ban)).

## Журнал действий {#the-activity-log}

- Каждое изменение, сделанное ключом (любой запрос, кроме `GET` и `HEAD`), записывается как «Изменение через API-ключ» с методом и путём, например `POST /api/sites/3/git/deploy`.
- Пользователь в этих записях — ваше имя пользователя и имя ключа, например `admin (key deploy-bot)`. Так же подписаны записи о том, что сделал запрос, например «Развёртывание из Git».
- Отклонённые запросы с ключом записываются как «Отклонение запроса по API-ключу», создание и отзыв ключей — как «Создание API-ключа» и «Отзыв API-ключа».
- Чтение не записывается. В списке ключей видно, когда и откуда каждый ключ использовался в последний раз.

Сам ключ никогда не записывается ни в один журнал.

## Советы по безопасности {#security-advice}

- **Используйте ключи только для чтения, где это возможно.** Мониторингу и отчётам нужен только `GET`.
- **Один ключ на скрипт.** Его имя видно в журнале, и его можно отозвать, не сломав остальные.
- **Разрешайте только те адреса, которым это нужно**, например ваши раннеры CI или сервер резервного копирования, если у них фиксированные адреса.
- **Задавайте ключам срок действия и меняйте их**: создайте новый ключ, пропишите его в скрипте, затем отзовите старый.
- **Не храните ключи в репозиториях и адресах.** Используйте хранилище секретов вашей CI или файл, доступный для чтения только владельцу, а в командах — переменную, чтобы ключ не попал в историю оболочки.
- **Сразу отзывайте ключ, если он мог утечь**, затем проверьте в **Последние действия**, что он делал.
- Если [брандмауэр](./security#firewall-ufw) ограничивает порт панели некоторыми адресами, разрешите там и адрес скрипта.
