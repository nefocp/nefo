# Сайты

Сайт в Nefo — это домен, который обслуживает единственный веб-сервер сервера: Nginx, Apache или OpenLiteSpeed. Это может быть сайт на PHP, статический сайт, приложение (Node.js, Python или Java) за прокси или обратный прокси на другой адрес. Каждый сайт получает собственного пользователя Linux, папку и, при желании, учётную запись SFTP; его можно клонировать, создать его резервную копию или удалить его из настроек сайта.

На этой странице описаны веб-сервер, создание сайта и все настройки сайта: домены, PHP, правила перезаписи, параметры доступа, SFTP, статистика трафика, журналы, клонирование и удаление. Сертификатам посвящена отдельная страница, [SSL-сертификаты](./ssl), как и [блокировке по странам и блокировке файлов](./website-protection).

## Какой веб-сервер выбрать? {#choose-the-web-server}

На сервере одновременно работает один веб-сервер, и Nefo настраивает под него каждый сайт. Перед добавлением первого сайта страница **Сайты** предлагает выбрать его:

| Веб-сервер | Когда выбирать | Память в простое |
|---|---|---|
| Nginx | Вашим сайтам не нужны файлы `.htaccess`. Это самый лёгкий вариант. | около 15 MB |
| Apache | Ваши сайты зависят от файлов `.htaccess`, например плагины WordPress или сайты, перенесённые с виртуального хостинга. | около 40 MB |
| OpenLiteSpeed | Вам нужны правила перезаписи из файлов `.htaccess` и плагин LiteSpeed Cache для WordPress. Кроме того, он отвечает по HTTP/3. | около 26 MB |

Чтобы установить веб-сервер:

1. Откройте **Сайты**.
2. В разделе **Установить веб-сервер** выберите Nginx, Apache или OpenLiteSpeed.
3. Нажмите **Установить Nginx** (на кнопке указан выбранный сервер).

Nefo устанавливает веб-сервер и версию PHP вашего дистрибутива с PHP-FPM, затем открывает порты 80 и 443 в брандмауэре (ufw), а для OpenLiteSpeed ещё и 443/udp для HTTP/3. Это занимает от одной до трёх минут. OpenLiteSpeed устанавливается из собственного репозитория пакетов LiteSpeed, а его консоль WebAdmin остаётся выключенной.

Все три веб-сервера запускают PHP в отдельном пуле PHP-FPM для каждого сайта. Ограничивать число запросов от одного посетителя умеет только Nginx; остальные настройки работают одинаково на всех трёх.

### Переход на другой веб-сервер {#switch-to-another-web-server}

Nefo не умеет переносить существующие сайты на другой веб-сервер, потому что конфигурация каждого сайта написана для установленного. Чтобы сменить веб-сервер:

1. Удалите все сайты (см. [Удаление сайта](#delete-a-website)). Если они вам нужны, сначала создайте их резервные копии: см. [Резервные копии](./backups).
2. Откройте **Программы** и найдите карточку **Nginx, Apache или OpenLiteSpeed**.
3. Нажмите **Удалить** у текущего веб-сервера, введите его имя (`nginx`, `apache` или `openlitespeed`) и подтвердите.
4. Нажмите **Установить** у нужного веб-сервера.

При удалении веб-сервера папки сайтов в `/var/www`, сертификаты и учётная запись Let's Encrypt сохраняются. PHP остаётся установленным. Adminer удаляется, потому что ему нужен веб-сервер, а правила брандмауэра, которые Nefo добавила для сайтов (порты 80 и 443), удаляются.

Кроме того, Nefo не позволяет установить веб-сервер, пока на сервере установлен другой, даже если вы установили его сами: обоим нужны порты 80 и 443. В этом случае страница **Программы** показывает его как «установлен, но панель его не использует». Сначала удалите его.

## Создание сайта {#create-a-website}

1. Направьте A-запись DNS домена на IP-адрес вашего сервера, например `203.0.113.10`.
2. Откройте **Сайты** и нажмите **Добавить сайт**.
3. В поле **Домен** введите имя без `http://` и `www.`, например `example.com`.
4. Оставьте отмеченным **Также отвечать на www.example.com**, если сайт должен отвечать и на `www`. Nefo отмечает этот пункт сама, когда домен состоит из двух частей, как `example.com`.
5. Выберите **Тип** (см. таблицу ниже).
6. Нажмите **Создать сайт**.

Затем Nefo показывает «Сайт example.com готов. Загрузите файлы в /var/www/example.com/public.» Пока вы её не замените, на сайте открывается страница приветствия.

| Тип | Что делает сайт |
|---|---|
| **PHP 8.3** (по пункту на каждую установленную версию PHP) | Отдаёт ваши файлы и выполняет файлы `.php` этой версией PHP. |
| **Статический (только HTML)** | Отдаёт HTML, CSS, JavaScript и другие файлы. Без PHP. |
| **Приложение (Node.js, Python, Java…) за прокси** | Передаёт каждый запрос программе, которая слушает порт на этом сервере. |
| **Обратный прокси на другой адрес** | Передаёт каждый запрос на указанный вами адрес: другой сервер или службу на этом сервере, которой Nefo не управляет. См. [Сайты с обратным прокси](#reverse-proxy-websites). |

Тип сайта потом нельзя изменить: статический сайт не может стать сайтом на PHP, сайт-приложение не может стать сайтом на PHP или статическим, и сайт с обратным прокси тоже не может сменить тип. Вместо этого создайте новый сайт. Чтобы установить WordPress или другое приложение, см. [Магазин приложений](./apps). Docker-приложения получают оттуда собственный сайт.

Nefo не принимает недопустимый домен (международные имена записывайте в punycode, `xn--…`), имя, которое уже использует другой сайт, и домен, папка которого уже существует в `/var/www`.

### Сайты-приложения (Node.js, Python, Java) {#app-websites-node-js-python}

Для типа **Приложение (Node.js, Python, Java…) за прокси** форма запрашивает ещё два параметра:

- **Порт, который слушает приложение (127.0.0.1)**: порт от 1024 до 65535. Nefo не принимает собственный порт панели, 3306 (MariaDB), 6379 (Redis), 7809 (приёмник вебхуков Git) и порт, который использует другой сайт-приложение.
- **Команда запуска (необязательно)**: одна строка длиной не более 1000 символов, например `node server.js`. Nefo выполняет её в папке `app` сайта от имени пользователя Linux сайта, с заданными `PORT`, `HOST=127.0.0.1` и `NODE_ENV=production`. Она работает как служба systemd `panel-app-<user>.service` и перезапускается через 3 секунды после остановки. Оставьте команду пустой, если программа запускается иначе, например в Docker.

Поместите код в `/var/www/example.com/app` по [SFTP](#sftp-access) или с помощью [развёртывания из Git](./git-deploy), которое развёртывает сайт-приложение в эту папку. Затем в настройках сайта:

1. На вкладке **Среда выполнения** в поле **Среда выполнения** выберите **По умолчанию для сервера (node в /usr/local/bin)**, версию Node.js, установленную на странице **Программы**, Python (`app/.venv`), для которого нужен Python, установленный на странице **Программы**, или версию Java, установленную на странице **Программы**: она показывается, например, как «Java 21 (OpenJDK 21.0.9)». На той же вкладке меняется **Команда запуска (необязательно)**. Нажмите **Сохранить**.
2. На вкладке **Обзор** в разделе **Программа приложения** нажмите **Установить зависимости**. Для `package.json` Nefo выполняет `npm ci` (или `npm install`, если нет `package-lock.json`). Для Python она создаёт виртуальное окружение `app/.venv` и устанавливает `requirements.txt` через pip. Это выполняется от имени пользователя сайта, до 20 минут.
3. Нажмите **Перезапустить** (или **Запустить**), чтобы запустить приложение с его зависимостями.

Карточка **Программа приложения** появляется, когда у сайта есть команда запуска. На ней также есть **Остановить** и **Журналы приложения**. На вкладке **Обратный прокси** можно изменить порт. Веб-сервер передаёт запросы на `127.0.0.1` на этот порт, с адресом посетителя в `X-Real-IP` и `X-Forwarded-For`, и подключения WebSocket работают. Чтобы передавать запросы на другой сервер или службу на этом сервере, которую Nefo не запускает, создайте вместо этого [сайт с обратным прокси](#reverse-proxy-websites).

Когда появляется первый сайт-приложение на Java, в списке сайтов рядом с фильтрами для других типов появляется фильтр **Java**.

#### Сайты-приложения на Java {#java-app-websites}

Для программы на Java укажите в поле **Команда запуска (необязательно)** команду, которая её запускает, например `java -jar app.jar`, и поместите `app.jar` в `/var/www/example.com/app`. В поле **Среда выполнения** выберите версию Java. Сначала установите Java на странице **Программы** (см. [Java](./software#java)).

- Служба приложения получает `JAVA_HOME` этой версии, а её папка `bin` стоит первой в `PATH`, так что `java` — это именно эта версия. Помимо `PORT` и `HOST=127.0.0.1`, которые получает каждый сайт-приложение, она получает `SERVER_PORT` (тот же порт) и `SERVER_ADDRESS=127.0.0.1`, которые читает Spring Boot. Поэтому приложение Spring Boot слушает нужный порт и только на этом сервере, без собственных настроек. Другие фреймворки читают `PORT` или требуют указать его в своей настройке.
- Для среды выполнения Java появляется **Лимит памяти (MB)**. Он задаёт максимальный размер кучи Java (`-Xmx`), от 32 до 65536 MB, через `JDK_JAVA_OPTIONS`, которую читает каждый `java`, запускаемый командой запуска, в том числе из скрипта запуска. Если оставить поле пустым, Java берёт до четверти памяти сервера. Процесс использует немного больше памяти, чем его куча. Java выводит `NOTE: Picked up JDK_JAVA_OPTIONS: -Xmx512m` в начале журнала, который открывает **Журналы приложения**.
- Скрипты [развёртывания из Git](./git-deploy) этого сайта выполняются с теми же `JAVA_HOME` и `PATH`, поэтому `./mvnw package` или `./gradlew build` собирают проект версией Java сайта. Лимит памяти на них не распространяется.
- **Установить зависимости** для сайта на Java не предлагается: соберите jar в скрипте развёртывания или перед загрузкой.
- Версию Java, которую использует сайт, нельзя удалить на странице **Программы**. Сначала выберите другую среду выполнения или удалите сайт.

## Сайты с обратным прокси {#reverse-proxy-websites}

Сайт с обратным прокси передаёт каждый запрос на выбранный вами адрес: сайт или приложение на другом сервере или службу на этом сервере, которой Nefo не управляет, например программу, которую вы запустили сами, или контейнер вашего собственного проекта Compose. У такого сайта есть свой домен, HTTPS-сертификат, параметры доступа и веб-брандмауэр, как у любого другого сайта. Он работает с Nginx, Apache и OpenLiteSpeed.

1. Откройте **Сайты** и нажмите **Добавить сайт**.
2. Введите **Домен** и выберите тип **Обратный прокси на другой адрес**.
3. В поле **Передавать на** введите адрес: `http://` или `https://`, имя хоста или IP-адрес, при необходимости порт и путь, например `http://198.51.100.7:8080` или `https://backend.example.com/app`.
4. Выберите **Отправляемый заголовок Host**: домен этого сайта или хост целевого сервера.
5. Нажмите **Создать сайт**.

Nefo показывает «Сайт example.com создан. Он начнёт передавать запросы на …, как только его домен будет указывать на этот сервер.» Адрес сохраняется вместе с портом, поэтому `https://backend.example.com/app` показывается как `https://backend.example.com:443/app`.

Путь запроса добавляется после пути адреса: с `http://198.51.100.7:8080/app` посещение `https://example.com/shop?page=2` попадает на `http://198.51.100.7:8080/app/shop?page=2`.

### Параметры {#the-options}

Меняйте их на вкладке сайта **Обратный прокси** и нажимайте **Сохранить**. У нового сайта с обратным прокси WebSocket и заголовки X-Forwarded-\* включены, а время ожидания — 60 секунд.

| Параметр | Что делает |
|---|---|
| **Передавать на** | Адрес, как описано выше. |
| **Отправляемый заголовок Host** | Домен сайта: передаётся домен, который запросил посетитель; этого ждёт большинство приложений за прокси. **Хост целевого сервера**: передаётся собственное имя целевого сервера (с портом, если он не 80 и не 443) — для сервера, который отвечает только на своё имя. Собственный адрес целевого сервера в перенаправлениях (`Location`) тогда заменяется адресом сайта. |
| **WebSocket** | Пропускает подключения WebSocket (чаты, обновления в реальном времени, терминалы). |
| **Заголовки X-Forwarded-\*** | Сообщает целевому серверу адрес посетителя и то, пришёл ли запрос по HTTPS: `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host` и `X-Real-IP`. Когда параметр выключен, эти заголовки удаляются, в том числе те, что отправил посетитель. |
| **Время ожидания (секунды)** | Сколько времени целевой сервер может отвечать, от 5 до 3600 секунд. Само подключение должно открыться за 30 секунд (или за время ожидания, если оно меньше). Если целевой сервер медленнее, посетитель получает страницу ошибки: 504 с Nginx, 502 с Apache. |
| **Не проверять сертификат целевого сервера (самоподписанный)** | Показывается для адреса `https://`. Принимает любой сертификат целевого сервера. |

::: warning
С параметром **Не проверять сертификат целевого сервера (самоподписанный)** подключение к целевому серверу остаётся зашифрованным, но любой, кто может его перехватить, сможет выдать себя за целевой сервер. Используйте его только для целевого сервера в вашей собственной сети с самоподписанным сертификатом.
:::

Без этого параметра Nginx и Apache проверяют сертификат целевого сервера `https://` по центрам сертификации сервера (`/etc/ssl/certs/ca-certificates.crt`) для имени из заголовка Host: домена сайта или хоста целевого сервера, если вы выбрали его. Самоподписанный или просроченный сертификат приводит к тому, что посетитель получает страницу ошибки (502 с Nginx, 500 с Apache).

### Что Nefo не принимает {#what-nefo-refuses}

- адрес, который не является адресом `http://` или `https://` с именем хоста или IP-адресом, необязательным портом (от 1 до 65535) и путём, например адрес с именем пользователя, строкой запроса (`?`), фрагментом (`#`), пробелами, `..` в пути, или адреса `0.0.0.0` и `::`;
- имя хоста, которое не удаётся найти («Имя хоста … не найдено. Проверьте его или используйте IP-адрес.»);
- саму панель: порт панели или `7809` (приёмник вебхуков Git) на этом сервере — неважно, пишете ли вы `127.0.0.1`, `localhost`, один из IP-адресов самого сервера или имя, которое на них указывает;
- порты 80 и 443 на этом сервере: сайт передавал бы запросы самому веб-серверу;
- **Время ожидания (секунды)** меньше 5 или больше 3600.

### Полезно знать {#good-to-know}

- С Nginx имя хоста разрешается в момент поступления запросов, через DNS-серверы из `/etc/resolv.conf`, поэтому имя, которое не разрешается при загрузке сервера, никогда не мешает Nginx запуститься. Эти запросы не читают `/etc/hosts`: для имени, которое знает только `/etc/hosts`, используйте его IP-адрес.
- HTTPS, перенаправление на HTTPS и HSTS работают так же, как для других сайтов: см. [SSL-сертификаты](./ssl).
- **Приостановить**, **Перенаправление**, защита паролем, заблокированные IP-адреса, ограничение частоты запросов, [блокировка по странам](./website-protection#block-or-allow-countries) и веб-брандмауэр действуют до того, как запрос дойдёт до целевого сервера.
- Вкладки правил перезаписи, своей страницы 404, защиты от хотлинкинга и блокировки файлов к сайту с обратным прокси не относятся и скрыты. Ваши собственные директивы (вкладка конфигурации веб-сервера) по-прежнему действуют.
- У сайта по-прежнему есть папка `/var/www/example.com` и пользователь Linux — для SFTP и резервных копий, но эти файлы он не отдаёт.

### С OpenLiteSpeed {#with-openlitespeed}

OpenLiteSpeed передаёт запросы иначе, чем Nginx и Apache. Вкладка **Обратный прокси** сообщает об этом в примечании, и параметр **Не проверять сертификат целевого сервера (самоподписанный)** там не показывается:

- Он никогда не проверяет сертификат целевого сервера `https://`: самоподписанный сертификат работает и без этого параметра.
- **Время ожидания (секунды)** не применяется: у OpenLiteSpeed нет ограничения для ответа через прокси.
- Он не передаёт адрес посетителя в `X-Forwarded-For`: он отправляет `X-Forwarded-Host`, а для запросов по HTTPS — `X-Forwarded-Proto`. Когда **Заголовки X-Forwarded-\*** выключены, Nefo удаляет `X-Forwarded-For` (а `X-Real-IP` удаляется всегда); OpenLiteSpeed всё равно отправляет `X-Forwarded-Host`.
- Подключения WebSocket доходят до целевого сервера без пути из адреса (`/live`, а не `/app/live`) и не работают с целевым сервером `https://`.
- Пути, заголовок Host целевого сервера, пароль и заблокированные адреса работают так же, как с другими веб-серверами.

## Настройки сайта {#open-a-website-s-settings}

Нажмите на домен в списке или на **Настройки** в конце его строки. Настройки открываются на боковой панели с вкладками в четырёх группах. Некоторые вкладки показываются только для некоторых сайтов:

| Группа | Вкладки |
|---|---|
| **Основное** | **Обзор**, **Домены**, **PHP** (сайты на PHP), **Среда выполнения** (сайты-приложения), **Обратный прокси** (сайты с обратным прокси) |
| **Безопасность** | **SSL / HTTPS**, **Веб-брандмауэр (WAF)**, **Закрыть доступ**, **Блокировка по странам**, **Блокировка файлов** (кроме Docker-приложений и сайтов с обратным прокси), **Защита от хотлинкинга** (кроме сайтов с обратным прокси), **Проверка на вирусы** |
| **Конфигурация** | **Перезапись** (сайты на PHP и статические), **Кэш страниц** (сайты на PHP с Nginx и OpenLiteSpeed), **Конфигурация Nginx** (называется по вашему веб-серверу), **Перенаправление**, **Обратный прокси** (сайты-приложения: порт), **Страница 404** (кроме сайтов с обратным прокси) |
| **Обслуживание** | **WordPress** (сайты на WordPress), **Развёртывание из Git** (кроме Docker-приложений), **SFTP**, **Резервные копии**, **Мониторинг**, **Трафик**, **Журналы**, **Срок действия** |

На вкладке **Обзор** показаны поля **Папка** (с кнопкой **Открыть в Файлах**) и **Пользователь Linux**, домены, версия PHP или среда выполнения, веб-сервер, состояние HTTPS и брандмауэра. Нажмите **Добавить заметку**, чтобы написать одну строку (до 200 символов), которая показывается в списке под доменом, например имя клиента.

## Пользователь Linux и папки сайта {#the-website-s-linux-user-and-folders}

Каждый сайт получает собственного пользователя Linux, поэтому один взломанный сайт не может читать или изменять другие. Имя образуется из домена: `example.com` превращается в `example_com`, а `blog.example.com` — в `blog_example_com` (с `_2`, `_3`…, если имя занято). У пользователя нет пароля и оболочки, и он не может войти по SSH, если вы не включите [SFTP](#sftp-access). PHP сайта и его приложение работают от имени этого пользователя, а PHP может открывать только файлы внутри папки сайта.

| Путь | Что там хранится |
|---|---|
| `/var/www/example.com/public` | Веб-папка (корень документов). Сюда помещаются файлы вашего сайта. |
| `/var/www/example.com/logs` | `php-error.log`, ошибки PHP сайта. |
| `/var/www/example.com/tmp` | Временные файлы PHP, незавершённые загрузки и сессии. |
| `/var/www/example.com/app` | Только для сайтов-приложений: код программы. |
| `/var/log/nginx/example.com.access.log` и `.error.log` | Журналы веб-сервера для сайта (`/var/log/apache2` в Apache, `/var/log/openlitespeed` в OpenLiteSpeed). |
| `/var/lib/nefo/certs/example.com` | Сертификат сайта. |
| `/var/cache/nginx/nefo/example.com` | Только Nginx: [кэш страниц](#page-cache), когда он включён. |

Файлы веб-сервера и PHP-FPM, которые пишет Nefo, начинаются со строки «Managed by Nefo. Do not edit» (Управляется Nefo. Не редактировать). Nefo перезаписывает их, поэтому вносите изменения в панели.

## Домены и дополнительные домены {#domains-and-aliases}

На вкладке **Домены** в поле **Дополнительные доменные имена** перечислены другие имена, которые открывают тот же сайт, по одному на строку, например `www.example.com`. У сайта может быть до 20 таких имён. Каждое имя должно указывать на этот сервер и может принадлежать только одному сайту.

Wildcard-имя, например `*.example.com`, отвечает для каждого поддомена. Для его сертификата нужна проверка через DNS в Cloudflare: см. [SSL-сертификаты](./ssl).

Если DNS домена находится в Cloudflare, кнопка **Направить DNS сюда…** на той же вкладке после предпросмотра создаёт или обновляет A-записи (и AAAA-записи) всех этих имён: см. [DNS (Cloudflare)](./dns#point-a-website-to-this-server).

Если у сайта есть HTTPS и вы меняете его имена, Nefo сообщает «Доменные имена изменились. Получите новый сертификат, чтобы HTTPS охватывал их все.» Нажмите **Продлить сертификат**.

## Версия и настройки PHP {#php-version-and-settings}

На вкладке **PHP** сайта на PHP есть такие настройки:

| Настройка | По умолчанию | Допустимо |
|---|---|---|
| **Версия PHP** | версия, выбранная при создании | любая установленная версия PHP |
| **Лимит памяти (MB)** | 256 | от 32 до 4096 |
| **Наибольший размер загрузки (MB)** | 64 | от 1 до 4096 (за ним следует ограничение размера запроса веб-сервера) |
| **Наибольшее время работы скрипта (секунды)** | 300 | от 10 до 3600 |
| **Процессы PHP** | 5 | от 1 до 200 |
| **Режим процессов** | **Запускать по запросу (экономит память)** | или **Держать несколько наготове (быстрее для нагруженных сайтов)** |

**Процессы PHP** — это сколько запросов PHP сайта обрабатывает одновременно. Каждый процесс может занять память вплоть до лимита, поэтому произведение числа процессов на лимит памяти должно помещаться в оперативную память сервера.

Ради безопасности Nefo отключает `exec`, `passthru`, `shell_exec`, `system`, `proc_open`, `popen` и `pcntl_exec` на каждом сайте, потому что они позволяют взломанному сайту запускать программы на сервере. В разделе **Разрешить функции, отключённые ради безопасности** отмечайте функцию, только если она действительно нужна приложению.

Нажмите **Сохранить**. Если PHP-FPM или веб-сервер отклоняет результат, Nefo возвращает прежние настройки. Чтобы установить другие версии PHP или расширения, ionCube Loader или изменить `php.ini`, см. [Программное обеспечение](./software).

## Правила перезаписи и собственные директивы {#rewrite-rules-and-your-own-directives}

На вкладке **Перезапись** в поле **Правила перезаписи** предлагаются готовые правила для распространённых приложений: **По умолчанию (фронт-контроллер: index.php или index.html)**, WordPress, Laravel, Symfony, CodeIgniter 4, Drupal, Joomla, OpenCart, Nextcloud, Moodle и phpBB для сайтов на PHP, а также «Одностраничное приложение» и «Статический сайт (чистые URL)» для любого сайта. Вкладка показывает правила выбранного набора. В Nginx набор заменяет стандартный блок `location /`. В Apache собственный файл `.htaccess` сайта может заменить фронт-контроллер набора, а в OpenLiteSpeed фронт-контроллер срабатывает после правил `.htaccess` сайта. В обоих случаях защитные правила набора файлы `.htaccess` отменить не могут.

**Статический сайт (чистые URL)** отдаёт страницы без окончания `.html`, так, как на них ссылаются генераторы сайтов, например VitePress (с `cleanUrls`): `/docs/install` отдаёт `docs/install.html`, а `/docs/` — `docs/index.html`. Остальные файлы отдаются как есть, а для несуществующей страницы по-прежнему возвращается 404.

Набор phpBB предназначен для phpBB, который вы устанавливаете сами. Он отправляет адреса, которые не являются файлами, в `app.php` phpBB и никогда не отдаёт файлы настроек phpBB (`config.php`, `common.php`), его папки `cache`, `files` (вложения), `store` (резервные копии), `includes`, `phpbb` и `vendor`, а также `images/avatars/upload`: на них возвращается 403.

Следующая вкладка называется по вашему веб-серверу, например **Конфигурация Nginx**. В поле **Директивы Nginx** (или **Директивы Apache**, **Директивы OpenLiteSpeed**) можно добавить собственные директивы, до 32 KB, в синтаксисе веб-сервера:

- Nginx добавляет их внутрь блока `server` сайта, перед правилами перезаписи.
- Apache добавляет их в конец блока `VirtualHost` сайта.
- OpenLiteSpeed добавляет их в конец блока `virtualHost` сайта.

Веб-сервер проверяет новую конфигурацию до каких-либо изменений. Если он её отклоняет, Nefo показывает ошибку, а сайт продолжает работать как прежде. Нажмите **Показать весь файл конфигурации**, чтобы увидеть, что генерирует Nefo.

О файлах `.htaccess`: Apache их читает. OpenLiteSpeed использует из них только правила перезаписи, которые Nefo в течение нескольких секунд после изменения копирует в конфигурацию сайта. Nginx их игнорирует.

## Кэш страниц {#page-cache}

В Nginx вкладка **Кэш страниц** сайта на PHP включает для него кэш FastCGI Nginx: Nginx сохраняет каждую страницу, созданную PHP, и отдаёт её повторно, не запуская PHP и не обращаясь к базе данных. Включите переключатель **Кэш страниц**.

- Страница хранится 10 минут, несуществующая страница (404) — 1 минуту. Если PHP выдаёт ошибку или перестаёт отвечать, Nginx отдаёт последнюю копию, которая у него ещё есть.
- Nginx каждый раз обращается к PHP для запросов, отличных от GET и HEAD (формы), адресов с `?`, посетителей с cookie входа или корзины (WordPress `wordpress_logged_in_`, `wp-postpass_`, `comment_author_`, WooCommerce `woocommerce_items_in_cart`, `wp_woocommerce_session_` и собственный `PHPSESSID` PHP), а также для страниц в `/wp-admin/`, `/wp-login.php`, `/xmlrpc.php`, `/wp-json/`, `/wp-cron.php`, `/cart/`, `/checkout/` и `/my-account/`. Страницы, которые PHP помечает как приватные или отправляет с cookie, тоже не сохраняются.
- У каждого сайта свой кэш размером до 256 MB в `/var/cache/nginx/nefo/example.com`. Страница, которую никто не запрашивал в течение часа, удаляется.

После изменения страницы нажмите **Очистить кэш**: все посетители сразу получат новую версию. Иначе посетители, которые не вошли в систему, могут видеть старую страницу до 10 минут. При выключении кэша или удалении сайта его папка удаляется.

Чтобы проверить, что кэш работает, откройте страницу дважды в приватном окне или дважды выполните `curl -sI https://example.com/`: заголовок `X-Cache-Status` покажет `MISS`, затем `HIT` (`BYPASS` для перечисленных выше запросов). У статических файлов такого заголовка нет: Nginx и так отдаёт их напрямую.

В OpenLiteSpeed вкладка сообщает, что в него встроен собственный кэш страниц, LSCache: для WordPress установите плагин LiteSpeed Cache, другие приложения включают его правилами кэширования в `.htaccess`. У Apache в Nefo нет кэша страниц и этой вкладки.

## Приостановка, перенаправление и защита сайта паролем {#suspend-redirect-or-password-protect-a-website}

**Приостановка.** Выключите переключатель в столбце **Работает** в списке или **Сайт работает** на вкладке **Обзор**. Тогда посетители получают HTTP 503 с текстом «This website is temporarily unavailable.» (Сайт временно недоступен). Файлы и настройки остаются, а сертификат продолжает продлеваться. Чтобы приостановить несколько сайтов, отметьте их, выберите **Приостановить** в списке **Массовое действие** и нажмите **Применить**; **Возобновить** снова включает их.

**Перенаправление.** На вкладке **Перенаправление** отметьте **Перенаправлять каждый запрос на другой адрес** и введите **Адрес**, например `https://example.org`. Это постоянное перенаправление (301), которое сохраняет путь: `/page` ведёт на новый адрес с `/page` в конце. Перенаправление работает, только пока сайт работает.

**Пароль.** На вкладке **Закрыть доступ** в разделе **Защита паролем** отметьте **Защитить паролем** и введите **Имя пользователя** и **Пароль** длиной от 8 до 72 символов. Тогда браузер запрашивает их, прежде чем показать сайт. Чтобы позже сохранить текущий пароль, оставьте поле пароля пустым. Проверка Let's Encrypt и вебхуки Git по-прежнему доходят до сайта.

На той же вкладке можно заблокировать IP-адреса, а в Nginx — ограничить число запросов от одного посетителя: см. [Безопасность](./security#rate-limit-and-blocked-addresses). Чтобы не пускать посетителей из целых стран, см. [Блокировка по странам](./website-protection#block-or-allow-countries).

## Своя страница 404 и защита от хотлинкинга {#custom-404-page-and-hotlink-protection}

**Страница 404.** На вкладке **Страница 404** отметьте **Использовать свою страницу 404** и загрузите свою страницу как `public/404.html`. Страницы, которые обрабатывает само приложение, например страницы WordPress или Laravel, сохраняют свою страницу 404.

**Защита от хотлинкинга.** На вкладке **Защита от хотлинкинга** отметьте **Защита изображений и медиафайлов от хотлинкинга**. Тогда другие сайты получают HTTP 403, когда встраивают ваши файлы `jpg`, `jpeg`, `png`, `gif`, `webp`, `avif`, `svg`, `ico`, `bmp`, `mp4`, `webm`, `mp3`, `ogg` и `pdf`. Ваш собственный сайт, поисковые системы (Google, Bing, DuckDuckGo и Yahoo) и посетители, которые открывают файл напрямую, всегда его получают. В поле **Другие сайты, которым разрешено их показывать** можно перечислить до 20 других сайтов, по одному на строку.

## Дата окончания {#expiry-date}

На вкладке **Срок действия** укажите дату в поле **Дата окончания** и нажмите **Сохранить**. Сайт работает до конца этого дня (по времени сервера); после этого Nefo автоматически приостанавливает сайт. Проверка выполняется каждый час. Чтобы убрать дату, нажмите **Никогда**. В последние 7 дней список показывает под доменом «истекает» и дату. Это удобно для сайтов клиентов, оплаченных до определённой даты.

На той же вкладке есть **Приостановить этот сайт**, чтобы приостановить сайт сразу.

## Доступ по SFTP {#sftp-access}

SFTP позволяет вам или клиенту загружать файлы через FileZilla, WinSCP или любое приложение SFTP. Тогда файлы принадлежат пользователю сайта, как и должно быть. Для этого нужен установленный сервер OpenSSH.

1. Откройте вкладку сайта **SFTP** и отметьте **Разрешить вход по SFTP для этого сайта**.
2. Выберите, как учётная запись входит:
   - **Создать новый надёжный пароль**
   - **Задать пароль (не короче 12 символов)**, до 128 символов
   - **Оставить текущий пароль** (когда пароль задан)
   - **Без пароля: вход только по SSH-ключам**
3. Необязательно: вставьте **Открытые SSH-ключи (необязательно)**, по одному на строку, как в `authorized_keys`, до 50 ключей. Параметры вроде `command=` удаляются.
4. Нажмите **Сохранить**. Созданный пароль показывается один раз: скопируйте его сразу.
5. Подключитесь, используя показанные значения **Хост**, **Порт**, **Имя пользователя** и **Папка**. Хост — это адрес, по которому вы открыли панель, а порт — порт SSH сервера. Вкладка также показывает полный адрес, например `sftp://example_com@panel.example.com/var/www/example.com`.

Учётная запись заперта в папке сайта. Она видит только `/var/www/example.com`, по тому же пути, что в панели и в PHP, и не может выполнять команды или пробрасывать порты. Политика паролей сервера может отклонить выбранный вами пароль; тогда Nefo показывает причину. Пока [файлы сайта заблокированы](./website-protection#lock-a-website-s-files), учётная запись SFTP может изменять только папки с правом записи.

При выключении SFTP пароль и ключи удаляются, а открытые сеансы завершаются.

## Статистика трафика {#traffic-statistics}

Вкладка **Трафик** читает журналы доступа веб-сервера для сайта. Выберите **Период**: **Сегодня**, **7 дней**, **14 дней** или **30 дней**. Вкладка показывает:

- **Запросы**, **Посетители** (разные IP-адреса), **Объём трафика**, **Доля ошибок** (4xx и 5xx) и **Боты**
- запросы и посетителей по часам или по дням
- **Популярные страницы**, **Самые активные IP-адреса**, **Источники переходов**, **Браузеры** и **Боты и скрипты**

Проверки сертификатов и собственные проверки [мониторинга](#monitoring) панели не учитываются. Сервер хранит журналы примерно за 14 дней, поэтому более старый трафик неизвестен. Для очень больших журналов читаются только последние 5 000 000 строк. Столбец **Посещения, 7 дней** в списке сайтов берётся из тех же журналов.

## Журналы {#logs}

Вкладка **Журналы** показывает последние строки:

- **Журнал доступа (Nginx)** и **Журнал ошибок (Nginx)** (называются по вашему веб-серверу)
- **Ошибки PHP** для сайтов на PHP (`/var/www/example.com/logs/php-error.log`)
- **Журналы приложения** для сайтов-приложений и Docker-сайтов

## Мониторинг {#monitoring}

Вкладка **Мониторинг** каждые несколько минут проверяет, что сайт отвечает, и отправляет вам оповещение, если он не отвечает. Включите **Отслеживать этот сайт**; первая проверка выполняется сразу.

Панель запрашивает публичный адрес сайта, с `https://`, если у него есть сертификат (иначе `http://`), через DNS, как любой посетитель. Поэтому неверная DNS-запись, страница ошибки Cloudflare или просроченный сертификат тоже обнаруживаются. Панель следует перенаправлениям на собственные домены сайта (например, с `http://` на `https://` или на `www.`). Перенаправление на другой домен считается ответом.

| Настройка | Что делает | По умолчанию |
|---|---|---|
| **Проверка** | как часто: каждую минуту или каждые 2, 5 или 10 минут | каждые 5 минут |
| **Путь** | страница для запроса, например `/health`; строка запроса допускается | `/` |
| **Текст, который должна содержать страница** | необязательно; регистр букв не важен | пусто |
| **Считать ответы 4xx, например 404, недоступностью** | ответ 4xx не проходит проверку | выключено |

Проверка не проходит, если:

- ответ не пришёл за 10 секунд, домен не разрешается, подключение отклонено или сертификат истёк, не является доверенным или выдан для другого домена
- ответ — ошибка HTTP 500 или выше. Ответ 4xx означает, что сайт доступен, если только вы не считаете ответы 4xx недоступностью
- текста, который должна содержать страница, нет в первых 256 KB страницы

Сайт получает состояние **Недоступен** после 2 неудачных проверок подряд и снова доступен после одной успешной проверки. Тогда панель отправляет оповещение во все каналы из **Настройки** → **Оповещения** (см. [Оповещения](./mail-alerts#alerts)):

- когда сайт становится недоступен — с причиной, например «example.com is down (HTTP 502, 2 checks in a row)» (example.com недоступен, HTTP 502, 2 проверки подряд), и затем каждые 6 часов, пока он остаётся недоступным
- когда он снова доступен — с длительностью недоступности
- когда отдаваемый им сертификат истекает менее чем через 14 дней — не чаще раза в день

Вкладка показывает состояние и последнюю проверку, доступность за 24 часа и за 7 дней, среднее время отклика, график времени отклика за последние 24 часа и последние сбои с их причинами. Время отклика измеряется до получения заголовков ответа, включая подключение. В списке сайтов у отслеживаемого недоступного сайта в столбце **Работает** красным цветом показано **Недоступен**, а колокольчик уведомлений включает его в список.

- Проверки отправляют user agent `Nefo-Monitor/1.0`. На вкладке **Трафик** они не учитываются.
- Результаты хранятся 7 дней. При удалении сайта они удаляются.
- Приостановленный сайт не проверяется.
- Проверки выполняются на этом сервере. Они не могут сообщить, что недоступен весь сервер, или о проблеме в сети между вашими посетителями и сервером: для этого добавьте внешний сервис мониторинга.

## Веб-брандмауэр, проверка на вирусы, блокировка по странам, блокировка файлов и резервные копии {#web-firewall-malware-scan-country-blocking-file-lock-and-backups}

- **Веб-брандмауэр (WAF)**: ModSecurity с OWASP Core Rule Set для этого сайта: **Выключен**, **Только обнаружение: записывать атаки в журнал, ничего не блокировать** или **Блокировать атаки**. Сначала установите брандмауэр на странице **Программы**. См. [Безопасность](./security#web-application-firewall), где описана и вкладка **Проверка на вирусы**.
- **Блокировка по странам**: не пускать посетителей из некоторых стран или пускать только из некоторых. **Блокировка файлов**: сделать код сайта доступным только для чтения для его PHP и его учётной записи SFTP, кроме папок, в которые он должен писать. См. [Блокировка по странам и блокировка файлов](./website-protection).
- **Резервные копии**: **Создать копию сейчас** или запланировать резервное копирование **Каждый день в 03:00**. См. [Резервные копии](./backups).

## Клонирование сайта {#clone-a-website}

**Клонировать** копирует сайт на новый домен: чтобы начать новый сайт на основе существующего или попробовать изменения на копии. Это работает для сайтов на PHP, статических сайтов и сайтов с обратным прокси, сайтов-приложений (Node.js, Python, Java) и Docker-приложений из [Магазина приложений](./apps).

1. Откройте вкладку сайта **Обзор** и нажмите **Клонировать…** в разделе **Клонировать этот сайт**.
2. Введите **Домен копии**.
3. Оставьте отмеченным **Копировать базы данных, связанные с этим сайтом**, чтобы скопировать и их. Этот флажок не показывается для WordPress, база данных которого копируется всегда, и для Docker-приложений, данные которых копируются всегда.
4. Нажмите **Клонировать**. Во время копирования сайт продолжает работать; копирование выполняется как задача с журналом. Docker-приложение ненадолго останавливается, пока копируются его данные.
5. Направьте DNS нового домена на этот сервер, затем включите HTTPS на его вкладке **SSL / HTTPS**. Копия начинает работать по `http://`.

### Сайты на PHP, статические сайты и сайты с обратным прокси {#php-static-and-reverse-proxy-websites}

Копия получает:

- новый сайт того же типа (та же версия PHP, статический сайт или обратный прокси на тот же адрес с теми же параметрами) с собственным пользователем Linux, тем же приложением, настройками PHP, правилами перезаписи и собственными директивами. В ваших директивах папка старого сайта заменяется новой;
- копию папки сайта `/var/www/example.com`, принадлежащую новому пользователю, без `logs`, `tmp` и ключа развёртывания Git (`.ssh`). Символические ссылки копируются как ссылки; ссылка на место внутри папки старого сайта теперь ведёт в то же место в новой. В `public/.user.ini` старая папка заменяется новой;
- для каждой связанной базы данных MariaDB, MySQL или PostgreSQL — новую базу данных и пользователя того же вида с копией её данных, связанные с новым сайтом;
- фоновые программы сайта, остановленные (см. ниже).

Когда копия готова, Nefo показывает данные для подключения к новым базам данных MariaDB и MySQL (базы данных PostgreSQL — на странице **Базы данных**). В собственных файлах конфигурации приложения (например, `.env` или `config.php`) всё ещё указаны старая база данных и пользователь: замените их на новые. Файлы, в которых указана старая папка, например кэш настроек приложения, тоже по-прежнему её содержат.

### Сайты-приложения {#app-websites}

Копия сайта-приложения дополнительно получает:

- собственный порт, который выбирает Nefo; приложение получает его в `PORT`. Приложение, которое само задаёт свой порт, нужно перенастроить на новый;
- те же **Среда выполнения** и **Команда запуска (необязательно)**; в команде папка старого сайта заменяется новой. Служба копии `panel-app-<user>.service` запускается, когда файлы и базы данных скопированы;
- `node_modules` с его ссылками (`node_modules/.bin`) и виртуальное окружение Python `app/.venv`, которое работает в новой папке: пути в его скриптах, `pyvenv.cfg` и файлах `.pth` указывают на папку копии. Зависимости заново не устанавливаются;
- фоновые программы сайта с той же командой, папкой и переменными (пути к старой папке заменены), но в состоянии **остановлено**: пока копия не использует собственные базы данных и очереди, они работали бы с данными оригинала. Запустите их на странице **Фоновые программы**.

Среда выполнения по-прежнему должна быть установлена: если версия Node.js, Python или Java удалена на странице **Программы**, копирование отклоняется до начала.

### Docker-приложения {#docker-apps}

Копия сайта Docker-приложения — это новый сайт с новой установкой приложения:

- той же версии и с теми же образами, что и оригинал (даже если в Магазине приложений есть более новая), с собственными контейнерами, портами и теми же лимитами памяти;
- копия данных приложения из `/var/lib/panel-apps/<name>`, сделанная, пока оригинал остановлен: Nefo останавливает его, копирует данные и сразу же снова запускает. Файлы пользователя исходного сайта в копии принадлежат пользователю нового сайта;
- те же учётные записи и пароли, что у оригинала (скопированные данные создавались с ними); они показаны в разделе **Магазин приложений** → **Установленные**, как для любого приложения;
- адрес приложения, заменённый на новый домен, для приложений, которые берут его из панели (`url`, `DOMAIN` и подобные настройки приложения). Если приложение хранит свой адрес в собственных настройках, измените его там.

Сначала Nefo проверяет, хватит ли памяти и места на диске для копии (примерно размер данных приложения плюс 512 MB).

Nefo отказывается клонировать:

| Приложение | Почему |
|---|---|
| n8n | Копия повторно выполняла бы активные рабочие процессы (расписания и триггеры). Экспортируйте рабочие процессы и импортируйте их в новый n8n. |
| Odoo | Копия тоже выполняла бы запланированные действия и работала с почтовыми серверами: она отправляла бы те же письма, получала и удаляла бы письма из того же почтового ящика. Создайте резервную копию или установите новый Odoo. |
| Приложение, установленное до появления Магазина приложений | Сначала обновите его (**Магазин приложений** → **Установленные**), затем клонируйте. |

Копия приложения мониторинга, например Uptime Kuma, проверяет те же сайты и отправляет те же уведомления, что и оригинал: приостановите в одном из них то, что вам не нужно.

### WordPress {#wordpress}

Сайт на WordPress копируется как [тестовая копия](./wordpress#make-a-staging-copy): его база данных копируется всегда, `wp-config.php` направляется на копию, а адрес сайта заменяется везде, поэтому копия сразу работает. Поисковым системам предлагается не индексировать её; если копия будет самостоятельным сайтом, измените это в WordPress в разделе **Settings → Reading** (Настройки → Чтение). В отличие от тестовой копии, клон нельзя перенести обратно на сайт, с которого он сделан.

### Что не копируется {#not-copied}

Дополнительные домены, сертификат, защита паролем, перенаправления и настройки брандмауэра, блокировка по странам, блокировка файлов, задания cron, настройки развёртывания из Git, доступ по SFTP, мониторинг и расписания резервного копирования.

Если какой-то шаг не удаётся, Nefo удаляет всё, что создала для копии: сайт, его пользователя Linux, новые базы данных, скопированные фоновые программы, а для Docker-приложения — новые контейнеры и их данные. Оригинал продолжает работать.

## Удаление сайта {#delete-a-website}

1. Откройте вкладку сайта **Обзор**.
2. В разделе **Удалить этот сайт** нажмите **Удалить**.
3. В окне под заголовком **Вместе с сайтом удаляются:** перечислено, что удаляется вместе с сайтом (его Docker-приложение и данные, учётная запись SFTP, задания cron, фоновые программы, мониторинг, настройки развёртывания из Git, расписания резервного копирования).
4. Оставьте отмеченным **Сначала создать резервную копию сайта** (по умолчанию) или снимите отметку.
5. Отметьте **Также удалить его базы данных**, чтобы удалить и связанные базы данных. Если флажок не отмечен (по умолчанию), они остаются на странице **Базы данных** без привязки к сайту.
6. Введите домен для подтверждения и нажмите **Создать копию и удалить** (или **Удалить** без резервной копии).

### Резервная копия перед удалением {#the-backup-made-first}

Если отмечен пункт **Сначала создать резервную копию сайта**, Nefo сначала создаёт на этом сервере обычную резервную копию: файлы сайта и его базы данных MariaDB, MySQL и PostgreSQL, а для Docker-приложения — его данные во второй резервной копии типа **Приложение**. Сайт удаляется, только если резервная копия создана успешно. Если она не удалась, задача останавливается с сообщением «the backup failed, so example.com was not deleted» (резервная копия не создана, поэтому example.com не удалён), и ничего не удаляется.

- Резервная копия называется `example.com_before-delete_<date>-<time>.tar.gz` (и `<user>_before-delete_….tar.gz` для данных Docker-приложения) и лежит в `/var/backups/panel/site/example.com/`.
- Как и любая резервная копия, созданная вручную, она хранится, пока вы не удалите её на странице **Резервные копии**. Расписания удаляют только собственные копии, а расписания сайта удаляются вместе с ним, поэтому её ничто не удалит.
- Она остаётся только на этом сервере: в удалённое хранилище она не загружается. Если нужна удалённая копия, загрузите её со страницы **Резервные копии**.
- Удаление выполняется как задача с журналом. В журнале указано имя резервной копии.

::: warning
Без резервной копии файлы сайта (и его базы данных, если вы отметили **Также удалить его базы данных**) вернуть нельзя. Окно предупреждает об этом, когда вы снимаете отметку **Сначала создать резервную копию сайта**.
:::

### Можно ли вернуть сайт после удаления? {#bring-a-deleted-website-back}

Да, с помощью резервной копии, созданной перед удалением (или любой другой резервной копии сайта). На странице **Резервные копии** восстановите копию `…_before-delete_…` и введите домен для подтверждения. Восстановление заново создаёт сайт с его доменом, дополнительными доменами, версией PHP, правилами перезаписи, файлами и базами данных. Удалённая база данных возвращается с прежним паролем, который указан в восстановленных файлах; сохранённая база данных снова привязывается к сайту.

Заново не создаются: сертификат (получите новый на вкладке **SSL / HTTPS**), задания cron, доступ по SFTP, фоновые программы, перенаправления и защита паролем. Что именно создаёт восстановление, см. в разделе [Восстановление на новом сервере](./restore-new-server#restoring-a-website-that-doesn-t-exist-here).

Резервные копии, созданные в Nefo 0.24.1 и позже, запоминают тип сайта, поэтому сайт-приложение (Node.js, Python, Java) возвращается со своей средой выполнения, командой запуска, портом и ограничением памяти, а сайт с обратным прокси — со своим адресом и параметрами; сначала установите среду выполнения приложения на странице **Программы**. Копии, созданные более старыми версиями, запоминают только версию PHP, поэтому такой сайт возвращается как статический сайт: сначала заново создайте его с тем же доменом и типом, затем выполните восстановление. Для Docker-приложения снова установите приложение на тот же домен из раздела **Магазин приложений**, затем восстановите его резервную копию типа **Приложение**.

### Что Nefo удаляет и сохраняет {#what-nefo-removes-and-keeps}

Nefo удаляет:

- папку сайта `/var/www/example.com` со всеми файлами, включая репозиторий Git и его ключ развёртывания
- пользователя и группу Linux, а также доступ по SFTP
- конфигурацию веб-сервера, файл паролей и ваши собственные директивы
- пул PHP-FPM, службу приложения или Docker-приложение с его контейнерами, данными и неиспользуемыми образами
- сертификат, кэш страниц и журналы веб-сервера для сайта
- фоновые программы сайта, задания cron, которые выполняются от имени его пользователя, его расписания резервного копирования, мониторинг и настройки развёртывания из Git
- корзину сайта в разделе **Файлы** и его файлы, помещённые антивирусным сканером в карантин
- связанные базы данных, если вы отметили **Также удалить его базы данных**

Nefo сохраняет уже созданные вами резервные копии: они остаются на странице **Резервные копии**.

Тестовые копии WordPress: при удалении рабочего сайта, у которого есть тестовая копия, копия сохраняется, но перенести её на рабочий сайт уже нельзя; окно предупреждает об этом. Удаление тестовой копии не меняет её рабочий сайт.

Пока выполняется развёртывание сайта из Git, Nefo не позволяет его удалить («На сервере выполняется другая задача. Дождитесь её завершения.»). С резервной копией задача ждёт развёртывания, которое началось во время резервного копирования. Если какой-то шаг очистки не удаётся, сайт всё равно удаляется из панели, а Nefo перечисляет неудавшиеся шаги под заголовком «Некоторые шаги очистки не удались:» (в журнале задачи, если сначала создавалась резервная копия).

Через API: `DELETE /api/sites/{id}` с `{"confirm": "example.com", "delete_databases": false, "backup_first": true}`. С `backup_first` ответ — 202 с задачей. Без него сайт удаляется сразу (200, с предупреждениями).
