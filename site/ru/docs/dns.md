# DNS (Cloudflare)

Nefo не запускает DNS-сервер. Если DNS вашего домена размещён в Cloudflare, Nefo управляет его записями через API Cloudflare с помощью API-токена: добавляет, изменяет и удаляет записи, после предпросмотра направляет имена сайта на этот сервер, добавляет записи MX, SPF и DMARC вашего почтового сервиса и очищает кэш Cloudflare.

Токен сохраняется в разделе **Настройки** → **Cloudflare**. После этого:

- страница **DNS** в группе **Хостинг** левого меню показывает ваши зоны и их записи, добавляет, изменяет и удаляет записи и очищает кэш Cloudflare;
- **Направить DNS сюда…** на вкладке сайта **Домены** за один шаг направляет имена сайта на этот сервер;
- **Настроить почту** на странице DNS добавляет записи MX, SPF и DMARC почтового сервиса;
- wildcard-сертификаты проверяются через тот же токен: см. [SSL-сертификаты](./ssl#wildcard-certificates-through-cloudflare-dns).

Nefo обращается только к API Cloudflare, а токен никогда не появляется в журналах и сообщениях панели.

## API-токен {#the-api-token}

Для всего этого нужен один токен. Ему нужны следующие права для зон (доменов), которые вы используете на этом сервере:

| Право | Для чего |
|---|---|
| Zone → DNS → Edit | Просмотр, добавление, изменение и удаление записей, **Направить DNS сюда…** и проверка сертификатов через DNS. |
| Zone → Zone → Read | Просмотр зон с их статусом и тарифом. Без этого права список зон может остаться пустым или Cloudflare откажется показывать зоны. |
| Zone → Cache Purge → Purge | **Очистить кэш** на странице DNS. |

1. В панели управления Cloudflare откройте **My Profile → API Tokens → Create Token** (Мой профиль → API-токены → Создать токен).
2. Начните с шаблона **Edit zone DNS** (Изменение DNS зоны). Он даёт право Zone → DNS → Edit.
3. Нажмите **+ Add more** (+ Добавить ещё) и добавьте Zone → Zone → Read и Zone → Cache Purge → Purge.
4. В разделе **Zone Resources** (Ресурсы зоны) включите зоны, которые вы здесь используете, или все зоны учётной записи.
5. Создайте токен, скопируйте его и сохраните в Nefo: **Настройки** → **Cloudflare** → **API-токен** → **Проверить и сохранить**.

Если у токена нет какого-то права, Nefo называет его, например: «Cloudflare отказал: у API-токена нет права Zone → DNS → Edit для этой зоны.» Измените токен в Cloudflare (**My Profile → API Tokens**, затем **Edit** (Изменить) рядом с токеном), добавьте право для зоны и сохраните. При изменении токена его значение сохраняется, поэтому в Nefo ничего менять не нужно. Если вы удалили токен или перевыпустили его (roll), сохраните новый в разделе **Настройки** → **Cloudflare**.

## Страница DNS {#the-dns-page}

Страница показывает одну зону за раз. Если зон несколько, выберите нужную в списке вверху; рядом показаны её статус (**Активна** или **Ожидание**, пока DNS-серверы домена ещё не серверы Cloudflare) и тариф.

В таблице перечислены записи зоны: **Тип**, **Имя** (`@` — сама зона, `www` — это `www.example.com`), **Содержимое**, **Прокси** и **TTL**. Таблицу можно отфильтровать по типу или искать по именам и содержимому. Зона, в которой больше 5000 записей, показывает первые 5000; остальные смотрите в панели управления Cloudflare.

Nefo может добавлять и изменять записи A, AAAA, CNAME, TXT, MX и CAA. Записи других типов, например NS или SRV, показаны с пометкой «в Cloudflare»: меняйте их в панели управления Cloudflare.

### Добавление и изменение записи {#add-or-change-a-record}

Нажмите **Добавить запись** или **Изменить** в строке записи. Тип записи изменить нельзя: удалите её и добавьте новую. Nefo проверяет запись, прежде чем отправить её в Cloudflare:

| Тип | Что ввести |
|---|---|
| A | IPv4-адрес, например `203.0.113.10`. |
| AAAA | IPv6-адрес, например `2001:db8::10`. |
| CNAME | Имя хоста, псевдонимом которого является это имя, например `example.com`. Запись не может указывать на своё же имя. |
| TXT | Одна строка текста длиной до 2048 символов: обычный текст, который Cloudflare делит на строки по 255 символов, или `"quoted strings"` длиной до 255 символов каждая. Заключайте в кавычки всё значение целиком или не используйте кавычки вовсе. |
| MX | Имя хоста почтового сервера, например `mail.example.com`, и **Приоритет** от 0 до 65535 (серверы с меньшим числом пробуются первыми). |
| CAA | **Тег**: `issue` или `issuewild` с доменом центра сертификации, например `letsencrypt.org` (`;` не разрешает ни одному центру), или `iodef` с адресом `mailto:` или `https://`. **Флаги** — 0 или 128 для критичной записи. |

**TTL** — это **Авто** (на выбор Cloudflare) или фиксированное время от 1 минуты до 1 дня.

### Через прокси или только DNS {#proxied-or-dns-only}

Записи A, AAAA и CNAME могут работать **Через прокси** (оранжевое облако Cloudflare): тогда посетители попадают в Cloudflare, который передаёт веб-запросы на адрес и скрывает его. У записей через прокси TTL всегда автоматический. **Только DNS** (серое облако) отвечает самим адресом. Записи остальных типов всегда работают в режиме «Только DNS».

Прокси Cloudflare пропускает только HTTP и HTTPS на портах 80 и 443 (и нескольких других). Всё остальное оставляйте в режиме «Только DNS»: SSH, почту и панель.

::: warning Оставьте для имени панели режим «Только DNS»
Если вы открываете панель по имени вроде `panel.example.com`, оставьте для этой записи **Только DNS**. Прокси Cloudflare не пропускает порт панели, поэтому с оранжевым облаком панель по этому имени больше не откроется. Страница DNS и **Направить DNS сюда…** предупреждают, если запись работает через прокси.
:::

## Направление сайта на этот сервер {#point-a-website-to-this-server}

1. Откройте **Сайты**, затем вкладку сайта **Домены**.
2. В разделе **DNS в Cloudflare** нажмите **Направить DNS сюда…**.
3. Проверьте адреса и параметры:
   - **Публичный IPv4-адрес этого сервера**, взятый из сетевых интерфейсов сервера;
   - **Также опубликовать IPv6-адрес (AAAA)** — отмечено, если у сервера есть публичный IPv6-адрес;
   - **Через прокси Cloudflare (оранжевое облако)**.
4. Изучите предпросмотр: для каждого имени и типа показаны запись **Сейчас** и **После** с пометками **новая**, **изменена**, **удалена** или **без изменений**.
5. Нажмите **Применить**.

Nefo меняет только записи имён сайта — его домена и дополнительных доменных имён; записи других имён никогда не затрагиваются. Для каждого имени:

- одна A-запись указывает на этот сервер: существующая A-запись обновляется или создаётся новая, а другие A-записи этого имени удаляются;
- с IPv6 то же происходит с его AAAA-записями. Без IPv6 удаляются AAAA-записи, которые указывают на другой сервер, потому что посетители по IPv6 и Let's Encrypt попадали бы на тот сервер;
- CNAME-запись заменяется A-записью, если только она не указывает на другое имя сайта (`www` → `example.com` остаётся как есть);
- имена, которые не входят ни в одну зону, видимую токену, не затрагиваются, и предпросмотр их перечисляет.

Когда вы нажимаете **Применить**, Nefo заново вычисляет изменения. Если после предпросмотра записи в Cloudflare изменились, ничего не меняется, и Nefo показывает новый предпросмотр: «Записи в Cloudflare изменились после предпросмотра.»

Если сервер находится за NAT и у него есть только частный IPv4-адрес, Nefo сообщает: «На сетевых интерфейсах этого сервера не найден публичный IPv4-адрес». Введите публичный адрес, по которому доступен сервер. Nefo не запрашивает его ни у каких внешних сервисов.

### Let's Encrypt за оранжевым облаком {#let-s-encrypt-behind-the-orange-cloud}

Let's Encrypt проверяет сайт по обычному HTTP. Когда прокси включён, настройка Cloudflare **Always Use HTTPS** (Всегда использовать HTTPS; **SSL/TLS → Edge Certificates**) отвечает на эту проверку перенаправлением ещё до того, как запрос доходит до сервера, и получить сертификат не удаётся. Выберите одно из двух:

- выключите **Always Use HTTPS** в Cloudflare и вместо этого включите в Nefo [перенаправление HTTP на HTTPS](./ssl#redirect-http-to-https); или
- отметьте **Проверка через DNS (Cloudflare)** на вкладке сайта **SSL / HTTPS** и оставьте настройки Cloudflare как есть.

Когда у сайта появится сертификат, установите в Cloudflare режим шифрования **SSL/TLS** **Full (strict)** (Полный, строгий). В режиме **Flexible** (Гибкий) Cloudflare обращается к серверу по HTTP, а **Перенаправлять HTTP на HTTPS** снова отправляет его на HTTPS, и получается бесконечный цикл.

## Как настроить записи DNS для почты? {#set-up-email-records}

Nefo не размещает почтовые ящики (см. [Почта и оповещения](./mail-alerts)). Если ваша почта размещена в Google Workspace, Microsoft 365, Zoho Mail или у другого сервиса либо пересылается через Cloudflare Email Routing, Nefo может добавить записи DNS, которые нужны этому сервису:

| Запись | Что делает |
|---|---|
| MX | Указывает, какие серверы принимают почту для домена. |
| SPF (TXT-запись) | Указывает, какие серверы могут отправлять почту от имени домена. |
| DMARC (TXT-запись в `_dmarc`) | Сообщает принимающим серверам, что делать с почтой, которая не прошла проверки SPF и DKIM, и куда отправлять отчёты. |
| DKIM (TXT- или CNAME-запись) | Публикует ключ, которым ваш сервис подписывает почту. |

Ничего не меняется, пока вы не просмотрите список изменений и не примените его.

1. Откройте **DNS** и выберите зону.
2. Нажмите **Настроить почту**.
3. В поле **Почтовый сервис** выберите **Google Workspace**, **Microsoft 365**, **Zoho Mail**, **Cloudflare Email Routing** или **Другой сервис**.
4. Необязательно: в поле **Почтовый домен** введите имя в зоне, например `mail` для `mail.example.com`. Для самой зоны оставьте поле пустым.
5. Необязательно: заполните поле **Адрес для отчётов DMARC (необязательно)** и вставьте запись DKIM, если она у вас уже есть (см. ниже).
6. Нажмите **Показать изменения**. В таблице перечислены все записи со значениями **Сейчас** и **После** и с тем, что с ними произойдёт: новая, изменена, удалена, без изменений или другой сервис.
7. Нажмите кнопку применения, например **Применить 4 изменения**.

Если после предпросмотра вы изменили какое-либо поле, перед применением нажмите **Обновить предпросмотр**. Если тем временем записи в Cloudflare изменились, Nefo отказывается применять изменения и показывает новый предпросмотр.

### Что получает каждый сервис {#what-each-provider-gets}

| Сервис | MX-записи | SPF include |
|---|---|---|
| **Google Workspace** | `smtp.google.com`, приоритет 1 | `include:_spf.google.com` |
| **Microsoft 365** | `example-com.mail.protection.outlook.com` (ваш домен, в котором точки заменены дефисами), приоритет 0 | `include:spf.protection.outlook.com` |
| **Zoho Mail** | `mx.zoho.com` (10), `mx2.zoho.com` (20), `mx3.zoho.com` (50), с доменом выбранного варианта **Дата-центр Zoho**: zoho.com, zoho.eu, zoho.in или zoho.com.au | `include:zohomail.com` или `zohomail.eu`, `zohomail.in`, `zohomail.com.au` |
| **Cloudflare Email Routing** | `route1.mx.cloudflare.net`, `route2.mx.cloudflare.net`, `route3.mx.cloudflare.net` | `include:_spf.mx.cloudflare.net` |
| **Другой сервис** | Серверы, которые вы введёте в разделе **Почтовые серверы (MX)**, до 5, каждый со своим приоритетом | Домен из поля **SPF include (необязательно)** и адреса из поля **Адреса отправки (необязательно)**; если оба пусты — `mx` |

Некоторые подробности:

- **Google Workspace**: если в зоне уже есть старые MX-записи Google (`aspmx.l.google.com` и другие), Nefo сохраняет их и ничего не добавляет.
- **Microsoft 365**: Microsoft даёт каждому домену собственный хост MX. Сравните значение в предпросмотре с тем, что показывает для домена Microsoft 365 admin center (центр администрирования Microsoft 365). Если оно другое, выберите **Другой сервис** и введите его. MX-запись, которая уже указывает на Microsoft 365, сохраняется как есть.
- **Zoho Mail**: выберите дата-центр, адрес которого вы используете для входа. Для другого дата-центра Zoho выберите **Другой сервис** и введите значения, которые показывает Zoho.
- **Cloudflare Email Routing**: почта начнёт приходить только после того, как вы включите Email Routing для зоны в панели управления Cloudflare и добавите там адрес назначения. Существующие записи маршрутизации Cloudflare сохраняют приоритеты, которые им назначил Cloudflare.

### SPF: всегда одна запись {#spf-always-one-record}

У домена должна быть ровно одна запись SPF; из-за двух записей проверка SPF не проходит. Nefo никогда не добавляет вторую:

- Если в зоне есть запись SPF, Nefo сохраняет всё её содержимое, добавляет include сервиса и сохраняет её окончание (`-all`, `~all` или `?all`). Запись без окончания получает `~all`.
- Если в зоне несколько записей SPF, Nefo объединяет их в одну: изменяет первую и удаляет остальные.
- Если вы настроили SMTP-релей в разделе **Настройки** → **Электронная почта**, запись SPF разрешает и сервис релея (например, `include:sendgrid.net` для SendGrid, `include:mailgun.org` для Mailgun, `include:amazonses.com` для Amazon SES), чтобы почта, которую отправляют ваши сайты, проходила проверку. Предпросмотр об этом сообщает.
- Запись SPF, которой нужно больше 10 DNS-запросов (`include`, `a`, `mx`, `ptr`, `exists`, `redirect`), не проходит проверку у многих получателей. Предпросмотр предупреждает об этом; удалите include, которые вам больше не нужны.

### MX-записи другого сервиса {#mx-records-of-another-provider}

MX-записи, которые указывают на другой сервис, отмечены пометкой «другой сервис». Почта шла бы на оба сервиса, поэтому их нужно убрать: отметьте **Заменить существующие MX-записи**, чтобы удалить их. Пока вы этого не сделаете или сами не удалите эти записи, Nefo не применяет изменения.

::: warning
Почта перестаёт приходить к старому сервису, как только его MX-записи удалены. Сначала перенесите почтовые ящики.
:::

### DMARC {#dmarc}

Nefo добавляет `v=DMARC1; p=none` в `_dmarc`, а если вы заполнили поле **Адрес для отчётов DMARC (необязательно)**, — также `rua=mailto:` с вашим адресом. С `p=none` никакая почта не отклоняется: принимающие серверы только присылают отчёты. Когда отчёты покажут, что вся ваша почта проходит проверку, политику можно сделать строже (`p=quarantine`, затем `p=reject`), изменив запись на странице DNS.

Если в зоне уже есть запись DMARC, Nefo оставляет её как есть.

### DKIM {#dkim}

Ключ DKIM создаёт почтовый сервис, поэтому Nefo создать его не может. В разделе **Подпись DKIM** окно подсказывает, где найти ключ у вашего сервиса:

- **Google Workspace**: в Google Admin console (консоль администратора Google) откройте Apps → Google Workspace → Gmail → Authenticate email и создайте новую запись. Её имя — `google._domainkey`, тип — TXT.
- **Microsoft 365**: на портале Microsoft Defender откройте настройки DKIM для домена. Microsoft даёт две CNAME-записи, `selector1._domainkey` и `selector2._domainkey`; в окне есть строка для каждой.
- **Zoho Mail**: в Zoho Mail Admin Console (консоль администратора Zoho Mail) откройте настройки DKIM домена и добавьте селектор. Введите имя селектора, за которым следует `._domainkey`, и значение TXT.
- Для **Cloudflare Email Routing** запись DKIM здесь не нужна: Cloudflare сам добавляет нужное, когда вы включаете Email Routing.
- **Другой сервис**: запросите запись DKIM у своего сервиса.

Вставьте **Имя записи** и **Значение**, выберите **Тип** (TXT или CNAME) и посмотрите предпросмотр. Имя вроде `google._domainkey` относится к почтовому домену; полное имя тоже принимается. Запись DKIM с тем же именем заменяется. Оставьте значение пустым, чтобы добавить запись DKIM позже: когда она у вас появится, снова запустите **Настроить почту** с тем же сервисом. Затем завершите настройку у сервиса (Google: **Start authentication** (Начать аутентификацию); Microsoft и Zoho: включите или подтвердите DKIM).

Повторный запуск **Настроить почту** безопасен: записи, которые уже в порядке, показаны как «без изменений».

Каждая запись, которую Nefo добавляет, изменяет или удаляет, записывается в журнал действий, как и другие изменения DNS.

## Очистка кэша Cloudflare {#purge-cloudflare-s-cache}

Когда прокси включён, Cloudflare хранит копии ваших файлов. Изменив их, нажмите **Очистить кэш** на странице DNS:

- **Всё** очищает кэш Cloudflare для всей зоны. Затем Cloudflare заново загружает каждый файл с сервера, поэтому несколько минут сайты могут работать медленнее;
- **Эти URL** очищает до 30 адресов зоны за раз, по одному в строке, например `https://example.com/style.css`.

Это кэш Cloudflare, а не собственный [кэш страниц](./websites#page-cache) сайта на этом сервере.

## Журнал действий {#activity-log}

Каждое изменение записывается в журнал действий (**Учётная запись** → **Последние действия**): «Добавление DNS-записи», «Изменение DNS-записи», «Удаление DNS-записи» и «Очистка кэша Cloudflare», с типом, именем и содержимым записи. **Направить DNS сюда…** записывает каждую запись, которую изменяет.

## Сообщения {#messages}

| Сообщение | Что сделать |
|---|---|
| `No Cloudflare API token is saved.` | Сохраните токен в разделе **Настройки** → **Cloudflare**. |
| `Cloudflare refused: the API token lacks the permission …` | Добавьте токену право, которое названо в сообщении: см. [API-токен](#the-api-token). |
| `Cloudflare did not accept this token.` | Токен неверный, просрочен или удалён. Создайте новый. |
| `None of these names is in a Cloudflare zone the API token can see` | Добавьте зону в **Zone Resources** токена или задайте записи там, где размещён DNS домена. |
| `Cloudflare does not answer for example.com yet (pending).` | Смените у регистратора DNS-серверы домена на два сервера, которые показывает Cloudflare. |
| `Cloudflare refused: …` | Собственное сообщение Cloudflare, например когда CNAME-запись и A-запись получили бы одно и то же имя. |
